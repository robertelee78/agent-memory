# Git sharing recovery foundation

The [portable recovery guide](../../skills/agent-memory/sharing/recovery/GUIDE.md)
describes the public `sharing_recovery.py` operations. The complete bank remains
canonical Markdown; no retry cursor, private receipt or shared mutable database
is needed to read it. Fresh server observations pin the actual configured
default branch and selected remote, without changing feature HEAD, index,
working files, remote tracking refs or FETCH_HEAD. Objects and a unique disposable
observation ref may be written; fetch errors never claim remote freshness.

Replay inventories actual authority history for the exact intended memory-only
delta in first-parent authority trees, including squash/recreated commit
identities and later corrections. A discarded merge-side candidate is not a
publication witness; the observed base must be provable within the bounded
authority mainline. A
prior successful landing and its current applicability are reported separately.
Unknown, rewritten or over-budget history requires reconciliation, never a
blind duplicate push. The helper never pushes or bypasses branch protections.

A previous observed shared-memory base may be outside feature-code ancestry.
It must remain reachable from authority; a memory-only import never requires
rebasing or merging authority code. Current feature HEAD stays pinned.

The three-way kernel preserves independent local/landed edits, structured route
maps, introductions, omissions and stable provenance. Tombstones from all three
snapshots are monotonic. Deleted payload versions are excluded even if locally
edited; derived observations need explicit erasure-closure review. An older
active version cannot override a known inactive version. Compatible bytes alone
are not semantic approval: every candidate stays review-required for the next
semantic reconciliation operation. The helper provides no canonical-write or
index-resolution API; approved callers use the existing recoverable writer and
recheck exact source, scope and Git pins.

Isolated public workflows cover offline/online inventory, a real competing
remote advance during fetch, lost successful responses, recreated candidates,
historical publication after correction, cursor loss, local untracked learning,
configured nested banks, terminal and inactive guidance, actual later ordinary
code merge and actual rebase. The existing writer applies the explicitly
reviewed mechanical candidate in those integration scenarios; automatic
publication, semantic approval and boundary refresh remain separate tasks.

Bounds are complete: 256 files, 16 KiB per file, 1 MiB per snapshot, 128
intervening commits for readback. Exceeding them refuses instead of claiming
absence or truncating evidence. No live credentials, client configuration or
repository is changed by contract tests.
