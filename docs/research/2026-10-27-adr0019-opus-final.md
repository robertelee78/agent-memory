# Review of ADR-0019 (proposed): checkout identity across device-number changes, and hook failure reasons

**Verdict: accept once the changes in section A are made.** The basic approach holds up. It reuses a binding only when the location, inode, project, bank, remote and authority all match, and it treats that match as continuity, never as authentication. That fixes the problem you saw without weakening ADR-0011's rules for independent clones and moves. Most of the problems are inconsistencies in the text, not flaws in the design.

**Limits of this review:** I reviewed only the ADR text you pasted. This session has no shell or file tools, so I didn't check the code claims against the repo: `project_identity.discover`, `scope_binding.require`, the hook catch-all, or `test_codex_stop`. I also couldn't run `awa status --json` or the agent-memory turn workflow. Nothing was edited or published, and any memory capture for this turn is still pending.

## A. Required changes

1. **The rule for choosing the key contradicts itself.** T1 says to use an exact current binding when one exists, but also says to use the lexicographically smallest of the equivalent keys. After `doctor --fix` adds the current key, those two rules can give different answers. Either answer changes the operation guards, which invalidates pending proposals. State one rule, for example: "exact observed key if registered; otherwise the minimum of the equivalent historical keys." Also define the ordering. Plain string comparison of `dev:ino` is fragile (`"9:…" > "16777230:…"`), so either compare `(dev, ino)` as numbers or say exactly how the key is encoded.

2. **"When it is absent" in T1 has an unclear antecedent.** Between "exact current binding" and "When it is absent" sit three sentences about moves and inode reuse, so it isn't clear what "it" means. Reorder T1 as:
   - the exact match
   - the conditions for historical recovery
   - the cases that are refused
   - how inode reuse is treated

3. **The failure-record key contradicts itself.** The text says "one record per canonical common-Git location", then says the key is the location *plus harness and adapter*, and later that "both Codex adapter records" are listed separately. Change it to "one record per (location, harness, adapter)."

4. **The catch-all has no fallback code.** The incident was caused by a catch-all that threw away the stage. With a fixed list of codes, any unexpected exception will either be forced into a misleading code or dropped again. Add something like `internal.unexpected`, with the stage that was reached. Also map each code to its stage explicitly: `state.unavailable` and the `guidance` stage currently have no defined pairing.

5. **`identity.unresolved` is too broad for doctor to give useful advice.** The repair steps differ a lot between:
   - no binding at all (initialize or link)
   - more than one matching historical key (refused, relink by hand)
   - authority or remote mismatch
   - a new inode (re-clone or restore: relink)

   Either split these into separate codes, or say that doctor works out the distinction itself and the hook code stays generic.

6. **"Explicitly reported" conflicts with "remain quiet."** T1 requires recovery to be reported as recovered historical evidence. T3 says recovered routine turns stay quiet. Say where the report goes. Presumably: in the resolver result, `status` and `doctor`, but not in per-turn hook output.

## B. Strongly recommended

7. **Explain why `--fix` is worth running, or make it plainly optional.** Matching on location and inode already survives any future device change without a write. Persisting the current key mainly makes lookup exact, and the cost is invalidating pending proposals. Doctor should explain that trade-off and must not present `--fix` as required. Also state that the registry grows by at most one key per distinct device number per project. Since macOS can reassign device numbers on every boot, this will happen again and again; it isn't a one-off.

8. **The test seam for device changes.** A test can't change a real `st_dev`. T4 should require an injectable stat or discovery seam, so the tests for device change, inode replacement and conflicts don't depend on the platform.

9. **Keep path canonicalization stable.** Recovery depends on the canonical location being identical. Firmlinks (`/opt` vs `/System/Volumes/Data/opt`), case-insensitive volumes and symlinked parents can all change the canonical form between versions. Require the same canonicalizer as at registration, and add a test where the canonical form differs.

10. **Optional extra check: birth time.** The ADR accepts that inode reuse at the same path can't be told apart from continuity. On macOS and BSD, `st_birthtime` of the common Git directory (and `statx` on Linux) could be compared when it was recorded, which costs no Git writes. It wouldn't be required for old metadata. You could mention it under Alternatives, or record it from now on.

11. **Hygiene for the failure records.** Require atomic replacement (write a temporary file, then rename), `O_NOFOLLOW`/no-symlink handling, mode 0600 inside a 0700 directory, and a TTL or cleanup step for repositories that no longer exist.

## C. Minor

12. "bank canonical remote": say what happens when the remote is renamed or transferred. Refusal plus relink is fine, but the remote-change test should assert that outcome.

13. The sentence about the main checkout being behind origin/main is fine as an elimination step. Mark it as "ruled out" so it doesn't read as a contributing cause.

14. Name the device-change cases you've considered beyond macOS reboots: Linux btrfs subvolumes, overlayfs, and NFS remounts. They all fall under the same rules, but naming them makes the intended scope clear.

## What's already solid
- Refusing to adopt on a remote match or path match alone, and refusing copied banks and conflicting candidates.
- Read-only resolution that writes nothing. Repair goes through the existing preview/apply protocol with lock and read-set revalidation, and doesn't rewrite pending proposals.
- Failure records that contain no prompts, answers or exception strings. Not counting a hook exit or acknowledgment as published learning. Retrying a failed prompt instead of fabricating a receipt for it.
- In T4, checking separately that the recovered prompt creates its pending ledger, which separates the missing-ledger case from the identity case.

Once A1–A6 are fixed, I'd accept the ADR and start extracting tasks.
