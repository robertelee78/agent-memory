## 3. What the current product actually does

These observations come from the pinned source and from a disposable
walkthrough ([§14](#14-walkthrough-evidence-and-its-limits),
[`walkthrough.json`](data/2026-11-05-federation-catalog/walkthrough.json)). The
walkthrough used synthetic projects `alpha` and `beta` in a temporary test world
with no network. No federation exists today. These observations bound what a
future design can reuse.

| ID | Observation | Evidence | Consequence for a catalog |
| --- | --- | --- | --- |
| O1 | Each bank carries a random UUIDv4 project ID. Two projects receive distinct IDs. | walkthrough O1; ADR-0011 | A member key can be a stable random ID, never a name. |
| O2 | Remote normalization merges HTTPS, SSH and SCP syntax, strips credentials and trailing `.git`, and lowercases github.com paths. Different hosts, owners and forks stay distinct. | walkthrough O2; `remote_identity.normalize` | A sanitized `repo://host/path` can be a location alias. It is not an identity. |
| O3 | A linked worktree resolves to the same project and is resolved. | walkthrough O3 | Worktrees MUST NOT become separate members (UC-d). |
| O4 | An independent clone with the same authority shows the same bank ID. It stays unresolved until an explicit `link`; preview writes nothing. | walkthrough O4 | "Same ID seen in a checkout" is not proof of membership; resolution must be explicit. |
| O5 | A changed remote (fork/rename/migration) stops with "explicit rebind or fork decision required". `fork` previews a new random ID. | walkthrough O5 | A fork is a new non-member. A rename keeps the UUID and only the location alias changes. |
| O6 | Two repositories with the same basename and no remote get distinct IDs. | walkthrough O6 | Directory names cannot be membership evidence. |
| O7 | `scope_policy decide` with another project's bank returns `applicable:false`, reason `different-project`, `identity_authenticated:false`. The `project:<id>`, `federation_consent:true` and `personal` variants are rejected as invalid. | walkthrough O7; `scope-policy.json` `"cross-repository": "unavailable-in-v0.0.1…"` | No cross-project path exists to extend. A consent flag cannot be simulated in the request. |
| O8 | Retrieval with another project's ID against `beta` exits 1 with a generic error. It discloses neither beta's body canary nor beta's ID, with or without `discovery`. Own-project retrieval returns `excluded_counts`, `metrics.inventory_files`, `entries`, `qualified_candidates` and similar counts. | walkthrough O8; `retrieval.py:221-242,291-296` | The local result envelope **reveals counts**. A foreign result MUST NOT reuse it per project (§9.2 rule D-3). |
| O9 | One developer ID resolves in both projects; the projects stay distinct; `identity_authenticated:false`. The boundary text says developer IDs are "not authentication, memory ACLs or personal memory namespaces". | walkthrough O9; ADR-0011 | Developer identity cannot be membership, R or X. |
| O10 | `MEMORY.md` publishes the project UUID and sanitized canonical remote to every repository reader. | walkthrough O10 | The UUID is not a secret or a credential. Possessing it MUST NOT prove membership. In a private repository, the UUID and remote are private metadata. |
| O11 | The source tree contains no `recall-policy` implementation. The installed `am 0.0.14` rejects `am recall-policy` as an invalid choice. | walkthrough O11; installed CLI help observed 2026-11-05 | #253's command does not exist. Its interface below is proposed. |
| O12 | Retrieval with `discovery` loads the repository's private recall catalog (`recall_catalog.load_catalog`) **before** `scope_binding.require` checks the project ID. On a mismatch the result is still refusal. | `retrieval.py:221-238` | Opening a cache optimistically before the authority check is harmless within one project. It MUST NOT be copied to a foreign path, because denial must come before any foreign index is opened. |
| O13 | Direct filesystem/Git access bypasses mediation. Someone who can read beta's checkout can read its bank without AM. | ADR-0006 | A catalog governs **mediated** discovery and disclosure only. It cannot make a readable repository private. |
| O14 | ADR-0010 places "optional federation manifests and federation-owned relations" in a separate, explicitly configured federation directory. A bank is complete without federation. | ADR-0010 §Non-project scopes, §usable bank | The manifest does not belong in `memory-bank/`. |

## 7. Identity and membership

### 7.1 Identity options

| Option | Description | Hard-filter result |
| --- | --- | --- |
| I1 UUID-backed manifest | Members are listed by the ADR-0011 project UUID, bound to a sanitized authority location alias and an approved name | **Passes.** Reuses O1–O6; survives rename/migration with a rebind; forks are distinct |
| I2 Remote-only identity | Members are identified by canonical remote | **Rejected.** Fails no-remote projects, host migration and multiple remotes (ADR-0011 alternatives; O5) |
| I3 Directory- or access-inferred membership | Any project the user can read, or that sits under a directory or organization, is a member | **Rejected.** ADR-0008 forbids inference from directory names or recent access. OP1 forbids access implying permission. O6 shows basename collisions. |

### 7.2 Identity edge cases

| Case | Current behavior | Proposed catalog consequence |
| --- | --- | --- |
| Cloned ID (independent clone) | Same UUID; unresolved until explicit `link` (O4) | Membership applies only to a **resolved** checkout. An unresolved clone is not a member (deny). |
| Same URL, different IDs | Bind refused: "Authority already identifies another project" (`test_canonical_remote_does_not_merge_different_bank_ids`) | The manifest rejects a second UUID at an existing authority location unless the steward records an explicit fork/new-project decision |
| Different hosts / forks | Distinct canonical remotes (O2); fork → new UUID (O5) | A fork is a new non-member. A `forked-from` link is itself D-governed metadata. |
| No remote | UUID plus local location only (`test_no_remote_move_keeps_id…`) | The entry has no shareable location. Verifying on another machine depends on an explicit link. Proposed: such members can be origins but stay non-discoverable as destinations until the steward records a location or an approved description. |
| Rename / host migration | Stops until explicit `rebind`; alias history kept (O5; ADR-0011) | UUID unchanged. The steward updates the location alias, so the manifest version changes and dependent projections are invalidated. Redirects are never followed automatically. |
| Multiple remotes | Authority remote required (`test_multiple_remotes_require_authority…`) | The manifest binds one authority location per member |
| Stale authority (registry or manifest disagrees with the checkout) | `resolved:false` with explicit issues | Unknown → `unavailable` (A6), never a best guess |
| Copied bank into an unrelated repository | Link or fork required (`test_copied_bank_requires_explicit_link_or_fork`) | The copied UUID does not inherit membership. The UUID plus authority-location binding mismatch denies. |
| UUID possession | UUID is readable in `MEMORY.md` (O10) | Never a credential (C4). A request naming a UUID that is not in the authorized set returns a constant-shape denial (§9.2 D-2). |
| Membership removal | n/a | Membership version increments; A5 invalidation; source bank untouched |

### 7.3 Proposed manifest research sketch (not a schema)

The manifest lives in a separate, explicitly configured federation directory or
repository (O14). It never lives inside `memory-bank/`. It is human-readable
and versioned:

- `federation.id` (random UUID); `federation.version` (monotonic); `steward`
  (who admits and removes; an attribution reference, not an authentication claim).
- Per member: `project.id` (ADR-0011 UUID); `authority_location` (sanitized
  `repo://` alias, optional for no-remote); `approved_name`;
  `approved_description` (owner-approved text; optional); `visibility_class`
  (`public` | `private`); `membership.accepted_by` and `membership.version`
  (mutual-acceptance reference); `metadata_grants` (D: which audiences may see
  this entry: `members` | specific member UUIDs | `public`).
- Typed links: `{from, to, type, approved_by_both, visibility}`, where type
  comes from a reviewed vocabulary (`depends-on`, `deployed-by`, `forked-from`,
  `shares-entity`). A link is D-governed metadata of **both** endpoints.
- `consent_refs`: references to #247 export grants (X). Grant content is never
  inlined.
- No bodies, counts, record lists, labels, paths, node/edge IDs or embedding
  references.

| Where membership is recorded | (R) repository-owned declaration in each member repository; (F) federation-owned manifest | R is simple and owner-controlled. A public repository declaring a private partner leaks the relation (C5). F keeps one auditable authority and respects ADR-0010. | F |

## 8. Public/private visibility and consent

### 8.1 Disclosure matrix by direction

Direction means source → destination (whose knowledge flows to whose agent).
Each cell is the **minimum** authority required before the item may be queried or
shown in a mediated result. "Public" repository visibility never substitutes for
any of these.

| Item disclosed | public → public | public → private | private → private | private → public |
| --- | --- | --- | --- | --- |
| Source existence / membership | M + D(source→dest audience) | M + D | M + D | M + D; publicizing requires a separate deliberate owner decision (A3) |
| Name / approved description | D | D | D | D plus that separate decision |
| Repository location alias | D (location may already be public) | D | D | D plus that decision; default hidden |
| Typed relation (link) | D from **both** endpoints | D both; the private destination's side is never shown to the public source (UC-c) | D both | D both; this is the highest-risk cell |
| Labels / counts / paths / graph node & edge IDs | D + X | D + X | D + X | D + X; default deny |
| Exported content (bodies, claims) | X per record-version + R + E (+P if remote provider) | same | same | same; #247 eligibility |
| Destination agent query reaching the source | E, after all of the above | E | E | E |

### 8.2 Consent options per cell

| Option | Description | Strength | Weakness |
| --- | --- | --- | --- |
| C-1 Deny by default, per-entry approval | Each metadata entry and each link is approved individually per audience | Least leakage; clear audit | Operator burden grows with links |
| C-2 Destination-specific approval | D granted per named destination project | Fits UC-b/UC-c asymmetry | Needs an approval per pair |
| C-3 Narrow standing grant with review/revocation | D for "all current members", reviewed periodically | Low burden for stable ecosystems | Silently widens when members join. Would need re-acceptance on every membership change. |

Metadata-minimal pointers (UUID plus approved name) against richer discoverable
summaries: a minimal pointer leaks existence only. A summary leaks topic,
technology and ownership. UC-c needs nothing on the library side. UC-b needs a
name and an owner, not a summary. **Proposed conservative disposition (not
approved):** C-1 for private-involving cells, C-2 allowed for private → private.
C-3 is only for all-public federations, and every membership change requires
re-acceptance. Approved names only; descriptions are optional and owner-approved.

### 9.1 The six authorities

| Letter | Authority | Granted by | Owner of design | Never implied by |
| --- | --- | --- | --- | --- |
| M | Catalog membership of a project in a federation | Steward + project owner (mutual) | #55 / #246 | Repository access, directory, organization, developer ID, UUID possession |
| D | Metadata discovery/visibility of an entry or link to an audience | Owner of that entry (both owners for a link) | #55 / #246 | M, public hosting |
| R | Destination acceptance plus per-reader read of foreign results | Destination owner; source owner's audience constraint | #246 names, #247 consumes | Repository read access, D |
| X | Source export of a record-version to a destination | Source owner | #57 / #247 | Admission, public repository, R |

### 9.2 Denial-before-query protocol (proposed)

Evaluation order for every cross-project operation:

1. **D-1 Local-only resolution.** Resolve the origin checkout (ADR-0011
   `resolved:true`) and read only the local, already-synchronized manifest,
   grant and receipt state. Open no foreign bank, index, cache, graph or network
   endpoint.
2. **D-2 Authorized set.** Intersect the requested destination UUIDs with the set
   for which M, D, R and current E hold, and for which X can apply. If the result
   is empty, or any authority version is unknown or stale, return one
   constant-shape outcome: `approval-required` (E missing) or `no authorized
   expansion destinations` (everything else). No reason is given per
   destination; the requested UUIDs are not echoed; nothing distinguishes "not
   a member" from "hidden" from "does not exist".
3. **D-3 Query.** Only now open foreign *exported* projections (#247) for the
   authorized subset. Results carry source project, evidence, validity, trust
   and scope (ADR-0008). No per-foreign-project `excluded_counts`, metrics or
   withheld markers. The local envelope's count fields (O8) MUST NOT be reused
   per project.
4. **D-4 Disclosure recheck.** Before returning results, recheck the authority
   versions (A14). On a mismatch, discard the results and return `unavailable`.
5. **D-5 Provider gate.** Semantic ranking that would send foreign text to a
   non-loopback provider requires P. Without P, only labeled exact/literal
   foreign recall is offered, never a semantic no-match (R3).

Timing: steps D-1/D-2 do no I/O that depends on foreign state, so denial latency
cannot reveal foreign size [INFERENCE: holds if implemented as specified; not
measured].

## 10. Revocation, removal and outage

The catalog side is below. Content-level state transitions, tombstones and
retained copies belong to #247 (A5, A6, A14).

| Event | Catalog effect (proposed) | Downstream |
| --- | --- | --- |
| Member removal (steward or owner) | `membership.version`++; entry disappears from every audience; links involving it become a generic "unavailable relation" with no target name | #253 receipts invalid; #56 foreign generation discarded; caches purged by version |
| D revoked for an audience | Entry or link hidden from that audience at the next evaluation | as above for that audience |
| X revoked | No catalog change; #247 semantics apply | #247 |
| Fork / rename / migration | Rename: location alias update, version++. Fork: new non-member. | revalidation |
| Federation unavailable / offline / manifest unreadable | Every cross-project request returns `unavailable`; local recall is unaffected (ADR-0008) | — |
| Manifest version newer than the cached grant | `unavailable` until refreshed (UC-f stale) | — |
| Copied/corrupt manifest, two conflicting manifests | `unavailable`; explicit steward repair | — |

Limits: revocation cannot erase bytes already disclosed to an agent, in a clone,
in Git history or held by a remote provider (ADR-0024 R4). The catalog can stop
*future mediated* disclosure only.

### 11.3 Recommendation (proposed; awaiting review and operator disposition)

1. **Defer catalog implementation (option N) until a concrete cross-project use
   case is confirmed** by the operator (and Vince, if the operator chooses). No
   case currently has confirmed demand (§6). Several are served by ordinary
   documentation, and the most valuable case (UC-b) is the most sensitive. Keep
   #55 unscheduled. Deferral is a valid research outcome (plan AC4).
2. **Adopt the boundary contract now as binding design input** for any future
   #55/#57/#253/#56 design, whatever option is chosen: A1–A14, C1–C8, the
   §8.1 matrix, the §9.2 denial-before-query protocol and the §9.3 interface
   split. This lets #253/#56 designs proceed without inventing a federation, and
   it adds no dependency to #257.
3. **If #55 is scheduled, use option F** in its minimal form: a federation-owned
   manifest in a separate federation directory, mutual enrollment, approved
   names, typed links approved by both endpoints, C-1/C-2 consent, no
   bodies/counts in the catalog, fail-closed `unavailable` offline. Option R is a
   possible all-public simplification only if the operator rules out private
   participation; choosing it would create a second convention.
4. **Reject** options L, G and A.

The least complex justified boundary today is N plus the contract in item 2.
