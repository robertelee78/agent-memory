# Native OMP session identity probe

Scope: actual installed macOS arm64 omp 18.16.0, executable SHA-256 `d4a10d97488d6054d2b18198bd24f461079952c7e0fb75ba66336ca0df0cb99e`. Source comparison pinned to upstream `650f3a108229ee11bf68ba3377f4e8c3391cd424` (binary/source equivalence not established). Research only; no product changes or real transcript reads. The extension's records and user-shaped message are explicitly **synthetic**, not human coverage. No provider/model invocation was made: slash-command `prompt_result` frames show `agentInvoked:false`.

Reproduce command: `python3 -I -B /tmp/agent-memory-omp-identity/probe.py`. `invocation-run5.json` records exact argv, minimal environment and cwd. All HOME, PI_CODING_AGENT_DIR, XDG, TMPDIR, session directory and cwd are under this scratch root. `OPENAI_API_KEY=synthetic-unused-not-a-credential` is a deliberately invalid placeholder, not live authentication. The driver keeps stdin open, correlates IDs and awaits local command `prompt_result`, then closes stdin and drains output. The executable exited 0, `stderr-run5.txt` is empty. Raw protocol: `requests-run5.jsonl`, `stdout-run5.jsonl`; public extension snapshots (including `getEntries()`, `getBranch()`, `getHeader()`, leaf, file existence): `observations.jsonl` (locate run 5 by initial session ID below); durable files: `sessions/`; code: `observer.ts`, `probe.py`.

## Observations from run 5

- Initial session `01a1a49b-3008-74d4-9b7e-549ba44f2dc0`: at session_start the allocated session path did not exist. After `pi.appendEntry` and `sessionManager.ensureOnDisk()` the file existed. Entries were model `ed865d35`, thinking `c8ece6cc`, synthetic custom `c26cfe87`, synthetic custom-message `594d7964`; leaf `594d7964`. Original getEntries and getBranch had the same four IDs in order. `ensureOnDisk` explicitly forced creation; this does not demonstrate that custom entries alone eagerly persist.
- `new_session` returned `cancelled:false`, session ID `01a1a49b-30df-70f1-958e-3ec43046cab8`, different file, and existing file at the new-session event. It did not contain the original IDs; synthetic custom was `ef15ef20` and custom-message `d8a26d9e`.
- `switch_session` to the initial scratch file returned `cancelled:false`, restoring the initial session ID and file and all four original entry IDs and leaf; both public snapshots matched. A separate native process started with `--resume` and the same scratch file also exited 0 and returned the same session ID and all four entry IDs. Exact argv/environment/stdin are in `invocation-restart.json`; raw frames in `stdout-restart.jsonl`, stderr empty.
- No-entry-ID `fork` returned `cancelled:false`, new session ID `01a1a49b-30e9-7788-a32a-e0e2ebe1514a`, distinct file, header `parentSession` equal to the original **session ID**. All four entry IDs, parent IDs and leaf persisted unchanged. Therefore an entry ID alone is not globally unique across session copies; session identity and lineage must be included in provenance.
- An extension command used public `ctx.newSession({setup})` and `manager.appendMessage` to insert a **synthetic user-shaped message**, not a human message. Session `01a1a49b-30ed-773b-bbd7-34052a96aa4b` contained message ID `442f73b4`. RPC `fork` with that entry ID returned `cancelled:false`; new session `01a1a49b-30f0-76af-bd2d-521fa4df8fe5` retained message `442f73b4` and the preceding two entry IDs. Its `parentSession` is the original **file path**, unlike whole-fork's session ID. Event was `session_branch`, versus whole fork's `session_switch`. This tests a synthetic fixture only; not actual human admission, tool batches, off-branch history or real-model paths.
- Public snapshot immutability does **not** hold deeply: `getEntries()` array, its custom entry and nested `data` were not frozen; the entry object from `getBranch()` was the same object as in `getEntries()` and repeated `getEntries()`. Writing nested fields through either reference was visible in subsequent snapshots and RPC `get_entries`, although popping the local arrays did not remove entries from the manager. On subsequent switch away/reopen, those unpersisted mutations were absent, while IDs survived. Thus a design depending on deeply immutable snapshots or automatic durable persistence of mutations is blocked; consumers must capture independent immutable evidence and must not treat mutation as a supported durable write. This does not prove all nested fields or rewrite timing behavior.
- Earlier credential-free run 2 started with no key, but `switch_session` refused with `Could not restore model openai/gpt-4.1`; the current session remained selected. In run 5 the synthetic placeholder made the same model discoverable for switching, with no model request. This is an observed startup-vs-switch distinction, not proof that a real provider credential works or that every configuration requires one. Raw evidence: `invocation-run2.json`, `requests-run2.jsonl`, `stdout-run2.jsonl`, `stderr-run2.txt`. Run 1 driver timed out on a buffered stdout read after native `new_session` had actually succeeded; captured as `stdout.jsonl`; subsequent driver fixed framing and awaited prompt completion. Run 4 did not wait for asynchronous local command completion; run 5 corrects that race.

No end-to-end agent-memory behavior, real human turn coverage, model/network behavior, permissions, steering, platform breadth or full integration qualification is claimed.
