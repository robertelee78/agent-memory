## 3. What the current source actually does (observed)

The cross-project export, grant, consent and federation surfaces are **absent**.
`scope-policy.json` declares cross-repository retrieval unavailable. No module
implements export, federation, a grant or consent for memory transfer. Everything
below is a same-project local invariant that a future export design must not
weaken. None of it is evidence that federation works.

The disposable scenario script
[`data/2026-11-05-export-governance/local_invariant_scenarios.py`](data/2026-11-05-export-governance/local_invariant_scenarios.py)
produced the evidence IDs A1–A9 and B1–B3. It ran against the real portable
helpers in throwaway `tests/world.py` worlds with synthetic project UUIDs and
bodies. Its output is recorded in
[`local_invariant_scenarios.json`](data/2026-11-05-export-governance/local_invariant_scenarios.json).
It ran on macOS (Darwin arm64) with Python 3.13.12, offline, with no network and
no provider.

Other observed fences:

- `projections.value` binds only `{schema, project_id, source_hashes, records}`.
- `recall_catalog.binding` binds `{repo_root, bank_root, project_id, repository_settings_sha256}` plus the engine generation.

Neither binds any membership, grant, policy or provider version. An authority
change that leaves the source bytes unchanged, such as a grant revocation, is
therefore **invisible to every current derived-artifact fence**. That is a
structural fact, not a defect for same-project use. A future export design must
add an authority-version vector to every foreign-derived artifact (§9.3).

## 4. Authority model: six independent decisions

The vocabulary is shared with #246 (join A2). All six decisions are conjunctive:
a missing, denied, unknown or unverifiable decision means deny. Model B1 checked
all 1,944 combinations (3⁵ grant states × mode × receipt × provider need). It
found 0 combinations that allow access without every required authority. The
override replaced the receipt in exactly 4 combinations, each of which already
had every other authority (the expected count is 1 + 3 = 4).

| Letter | Authority | Granted by (proposed) | Covers | Never implies | Revocation effect |
| --- | --- | --- | --- | --- | --- |
| M | Federation membership | Federation steward with the member's explicit enrollment (#246) | Being a named member of one federation (ADR-0008:48-51) | Any read, discovery, export or provider permission | Stop selection; purge that member's projected content in federation-owned stores; bank untouched |
| D | Metadata discovery/visibility | Source project, for its catalog metadata (#246) | Existence, name, description, location, typed relation, labels, counts, graph structure (ADR-0023:54-56) | Body or claim content (X) | Hide entry; invalidate metadata caches; denial happens before any foreign query (A9) |
| R | Destination acceptance and reader access | Destination project, for its audience (#246 names; #247 consumes) | That a named destination accepts foreign content for a declared reader audience | Source consent; widening beyond the source's declared audience | Stop serving; purge destination-side foreign caches |
| X | Deliberate source export | Source project authority through a trusted channel (§12) | One eligible record **version**, one named destination, one audience class, an expiry, a grant version | Membership, discovery, provider disclosure, re-export, later versions | Stop future disclosure; invalidate grant-keyed artifacts; minimal marker |
| E | Expansion approval | Operator, per request through a trusted channel (ADR-0023 D4), or a standing `allow` override within the already authorized set | Issuing one bound expansion without another prompt | M, D, R, X or P; it never widens the authorized set (ADR-0023:140-142) | Invalidate outstanding receipts and derived results before further disclosure (ADR-0023:143-144) |
| P | Provider/model disclosure | Operator for its own content (ADR-0024 R3). For foreign content, also the source (proposed default: deny) | Sending specific text or queries to a named non-loopback provider | X; and X never implies P (ADR-0024:161-162) | Stop sending; local vectors purged; provider-side copies stay outside AM's authority (ADR-0024:232-234) |

These do **not** constitute any of M, D, R, X, E or P: repository or Git readability, public hosting, OS or filesystem access, developer ID, local admission, being in the same organization, or having both checkouts (ADR-0006:48-56; ADR-0023:104; ADR-0008:37-39).

| Superseded, revoked, expired | Not eligible as current guidance. Exporting them as an explicitly historical view is an open option, with X and labelling (ADR-0024 R2 historical view) | `lifecycle.current`; A1 |

| Record with externally sourced evidence (URLs, tickets) | Eligible only if the evidence reference itself is disclosable to R. Otherwise export with the evidence withheld and the result labelled `evidence-not-disclosable`, never "verified" | §7.3 |
| Private identifiers inside bodies or metadata (developer UUID, session, harness, branch names, paths) | Minimized by default (§7.2) | ADR-0024:88 |

### 5.2 Summaries and pointers

Both redacted summaries and opaque pointers still need X: a summary is a derived
disclosure of the same knowledge. A summary is also a new authored artifact that
needs its own review, provenance (`derived-from` the exported version) and grant.
A pointer discloses existence, so it needs at least D. **Re-export** (destination
to a third project) and derivation from received content are **disallowed unless
a separate explicit policy exists**. X is non-transitive.

## 7. Provenance and access-scope envelope

### 7.1 Proposed envelope (research sketch, not a schema)

Each foreign result carries:

- source project UUID (ADR-0011) and record ID/version;
- immutable source reference (source blob/commit or record content hash, bound by the federation, not by the destination);
- lifecycle status and valid-time window at publication;
- trust, source class and kind;
- applicability conditions, carried verbatim;
- evidence references or `evidence-not-disclosable`;
- origin attribution class (see §7.2);
- grant ID/version, destination and audience class;
- the authority-version vector `{M, D, R, X, P, policy}`;
- federation projection generation and the time the authority was last checked.

The destination renders a foreign result as **foreign, source-labelled guidance**.
It is never native current guidance, never a binding procedure, and never subject
to native supersession. A native record may not be superseded or corrected by a
foreign one without ordinary local admission/governance.

Options:

- E1: the full envelope on every result;
- E2: a minimal envelope plus a fetch-on-demand provenance pointer, which costs one more authorized request;
- E3: snapshot-level provenance only (C3).

**Recommendation: E1.** E2 saves bytes but adds a second disclosure path that
must itself be authorized. E3 loses per-version revocation.

### 7.2 Attribution minimization

Developer UUID, harness and session are provenance, not ACLs (ADR-0006:52-56). In
a foreign result, **replace them with an attribution class** ("source-project
contributor, reviewed") unless X explicitly includes attribution. This prevents a
cross-project developer-activity correlation channel.

### 7.3 Undisclosable or unverifiable evidence

If evidence cannot be disclosed to R, or cannot be revalidated against the
source's current state, the result must either:

- withhold the record (abstain), or
- present it as `historical-bounded`: the source reference is shown, labelled not revalidated.

It must never be presented as verified or current. A result whose authority
cannot be re-checked is `unavailable`, not a no-match (A6; ADR-0023:57-58).

### 7.4 Information-minimal audit

The source side logs grant ID/version, destination, record IDs/versions and the
receipt digest. It logs no raw query (ADR-0023:144-145).

The destination side logs the receipt digest, destinations and outcome class.
Neither side logs counts of excluded foreign material, hidden-project names, or
per-project withheld counts (A1 shows these exist locally and must not be
forwarded). A denial returns only one of #246's constant-shape outcomes,
`approval-required` or `no authorized expansion destinations`, with no
per-destination reason and no echo of the requested UUIDs (join A9; #246 §9.2
D-2).

## 8. Request-bound expansion approval (E)

### 8.1 Receipt

A receipt binds:

- requesting harness session (or an operator-attested expiring session handle), project UUID, developer UUID;
- origin project and the exact destination set;
- query digest (not the raw query) and allowed operation (cue/retrieve/explore);
- page/continuation bound;
- policy revision and authority-version vector;
- expiry.

It is stored privately, outside any canonical bank (ADR-0023:144).

Model B2 checked reuse against this binding. Only `unchanged-page-2-retry` reused
the receipt. Each of the following required a new decision: page beyond bound,
changed query, added destination, policy revision, grant version bump, other
parallel session, new session after reset, other developer in the same project,
other origin project, retry after denial, and expiry.

### 8.2 Rules

| Situation | Proposed rule |
| --- | --- |
| Denial or cancellation | No foreign query is issued and no foreign metadata is read. No cache is populated. Nothing persists a "denied project" list. Local recall continues (ADR-0023:110-112). |
| Retry after deny/cancel | A new decision is required; a denial is not cached as "ask later = allow" |
| Paging/retry of the unchanged request within its bound | Reuses the receipt. Each page still rechecks the authority vector at disclosure time. |
| Query, destination or operation change; a new expansion | A new decision is required |
| Policy revision, or a grant or membership version change | Outstanding receipts and derived results are invalidated **before** the next disclosure (ADR-0023:143-144) |
| Session reset or a new session | Reset to the effective policy. A session override never carries over. |
| Parallel sessions | Isolated; a handle is not reusable across sessions |
| Developer isolation | A project override is private local configuration bound to project UUID and the local account. It is never Git-shared or another developer's preference. Threat limit: developer ID is attribution only, so isolation between people sharing one OS account cannot be stronger than that account (ADR-0006:52-56). |
| Project isolation | An override for project P1 never applies to P2, even for the same developer |
| Agent self-elevation (`allow` set by the agent, fabricated approval, reused handle, a boolean flag, a PTY) | Refused as approval-required, with no foreign disclosure. Changing to `ask` may be agent-invoked (ADR-0023:114-120). |

### 8.3 Precedence

Model B3 enumerated all nine combinations:

- session `ask` beats project `allow`;
- session `allow` beats project `ask`;
- an absent setting means `ask`.

This matches ADR-0023:137-138. **Proposed refinement:** a session `allow` can only
widen prompts within the already authorized set, so it cannot override an
X/R/M/D/P **deny** at any scope. A source-side revocation beats every local
override.

## 9. Revocation, removal and deletion as state transitions

### 9.1 Transition table (proposed)

"Controlled stores" means federation-owned projections, destination foreign caches, graph/vector generations and receipts that AM owns.

| Event | Future selection | Controlled caches/projections | Marker | Source bank | Already-disclosed copies |
| --- | --- | --- | --- | --- | --- |
| Publication (X issued) | Eligible version only, after commit-time recheck | New generation keyed by the authority vector | — | Unchanged | — |
| Scope narrowing (X audience/destination reduced) | Stop for removed audiences | Invalidate affected generations | Grant version bump | Unchanged | Outside authority |
| Correction (new version v+1) | v stops being current. The destination shows v as superseded/withheld **without disclosing v+1** unless v+1 has X (ADR-0024 R3 hidden replacement). | Invalidate v | Opaque `superseded` signal for the exported ID | New version | Outside authority |
| Revocation (status `revoked`) or X revoked | Stop immediately on the next authority check | Purge v | Opaque revocation marker | Unchanged/revoked | Outside authority |
| Deletion (tombstone) | Stop; never re-include under any conditions (A4) | Purge bodies, vectors, relation payloads, caches, snapshots/WAL in owned stores; fence old builders (ADR-0024:217-226) | Content-free marker: ID, source project, time, reason class (A5) | Tombstone | Outside authority |
| Member removal (M) | Stop all of the member's content | Remove its projected content (ADR-0008:70-71) | Membership version bump | **Not deleted** | Outside authority |
| Destination removal (R withdrawn) | Stop serving to it | Destination foreign caches purged when it next runs; federation stops serving | Grant version bump | Unchanged | The destination's own copies |
| Outage (source/federation unreachable) | `unavailable` (§10) | Keep, but do not serve past the authority-check horizon (§10 option O2) | — | Unchanged | — |
| Reconnection/rejoin/replay | Rebuild **only** from currently eligible exports under current versions | Discard any generation whose vector mismatches | — | — | — |

### 9.2 Races and in-flight queries

The authority check happens at disclosure (commit) time, not only at request
time. An in-flight page whose authority vector changed is discarded and reported
as `authority-changed; re-request`, never partially served. The current local
analogue is the double history read in `tombstones.filter_projection`
(`tombstones.py:94,107-109`) and the post-read rechecks in `projections.check`
(`projections.py:85-86`).

### 9.3 Stale builders: graph, vector and cache non-resurrection

Join A14 and ADR-0024 R4 apply:

1. A builder records the authority-version vector and source tombstone frontier at start.
2. Before atomically publishing a candidate generation, it re-reads both. A mismatch or an unknown value means discard.
3. Readers serve only one generation whose vector equals the current one.

Observed limit: the current fences cover source bytes only (A4, §3), so a grant-only revocation needs this new vector. Rebuild, rejoin or replay from a historical checkout, backup or cache MUST NOT reintroduce revoked or deleted IDs (ADR-0012:90-92; ADR-0024:223-225).

Cache authentication (HMAC in `recall_catalog.authenticate`) proves only cache integrity, never current authority (ADR-0024:225-226).

### 9.4 What revocation can and cannot promise

| Can be guaranteed (by AM-owned stores, after future implementation) | Cannot be guaranteed |
| --- | --- |
| Stop future selection and disclosure | Erasure of bytes already disclosed to a reader or agent context (A4: retained copy keeps the canary) |
| Invalidate and purge controlled projections, receipts and generations; fence stale builders | Independent clones, Git history, forks, public mirrors |
| Content-free markers | External backups, unless explicitly documented (ADR-0024:221-223) |
| Report `derived-erasure-pending` until owned copies are verified erased | Provider-side retention (ADR-0024:232-234) |
| | Bring-your-own stores that AM does not own (ADR-0024:228-231) |

The state vocabulary should keep these separate:

- `revoked` or `deleted` (canonical);
- `derived-erasure-pending`;
- `derived-erased-in-owned-stores`;
- `outside-authority`.

Nothing in this brief claims that production derived erasure exists. The local
purge receipt itself already says that Git history, remote copies and backups are
retained (`purging.py:257-260`).

### 9.5 External provider retention (optional, P)

Foreign content defaults to **local/loopback-only embedding** at the destination.
Sending it to a non-loopback provider requires both:

- the destination operator's P for that provider, and
- a source-side P term inside X that names a provider class.

The approval must show the provider's retention terms, or state that they are
unknown (ADR-0024:232-234). AM never claims that the provider erased anything.
Queries that contain foreign context are covered too. Query vectors are not
retained by default (ADR-0024:156-157).

## 10. Dangling links, outage and local independence

| Guarantee | Proposed statement | Source / evidence |
| --- | --- | --- |
| G-a | Removing any index, graph, vector store, catalog or federation cache leaves canonical Markdown untouched and readable | ADR-0008:68; A6; `test_bank_usability.py:59,103` |
| G-b | Federation unavailability never blocks local initialize, checkpoint, resume, search, validate or repair; no local operation waits on a foreign call | ADR-0008:43-46,69; A6 (destination recall exit 0 while source offline) |
| G-c | A relation to a missing or removed project is a federation-owned record rendered `unavailable` without the private target's name, existence or counts. Both banks remain valid; there is no silent link repair. It is never stored in canonical `derived-from`/`corrects`/`supersedes`. | ADR-0008:72; ADR-0023:96-97; A7, A9 |
| G-d | A stale, unauthorized or unverifiable foreign result is `unavailable`, never a clean no-match and never current qualified guidance | ADR-0023:57-58; A2, A6 |
| G-e | Recovery and rebuild source only currently eligible exports under current authority versions | ADR-0024:223-225; §9.3 |
| G-f (added) | Received foreign content is never written into a canonical bank | A9 (naive import broke destination recall) |

The outage options are:

- **O1, fail-closed foreign reads with local continuation.** Any foreign result needs a live authority check; during an outage, foreign recall returns `unavailable` and local recall proceeds.
- **O2, bounded offline reads under a valid grant.** Cached foreign results may be served for at most `min(grant expiry, authority-check horizon)`, labelled `last-verified-at` and `revocation-may-be-unobserved`.
- **O3, unbounded offline cache.** Rejected: revocation would never take effect.

**Recommendation: O1 as the default. O2 is available only if the operator
explicitly enables it per federation, with a short horizon** (Q4). Local
functionality is never weakened to make remote guarantees convenient.

## 12. Comparison and recommendation

### 12.1 Constraint-first filter

Options are rejected if they violate hard exclusions, consent, provenance/scope,
non-resurrection or local independence. That rejects:

- C0 and C4;
- O3;
- treating repository, organization or public-hosting access as X;
- transitive re-export;
- P inherited from X;
- writing received content or foreign relations into canonical banks (A7, A9);
- reusing local discard results as foreign deletion evidence (A2);
- forwarding per-reason or excluded counts across projects (A1).

### 12.2 Survivors (qualitative; no invented scores)

C1+E1+O1 has the lowest leakage and exact auditability, but the highest operator
effort. C2 trades some predicate-drift leakage for less effort, and is sensitive
to how often new versions appear. C3 is the simplest for public→public, but
revocation lags until the next snapshot. O2 improves offline usefulness in
exchange for a bounded revocation-observation delay. These comparisons follow
from the scenarios in §11 and the observed fences in §3. No performance or
security numbers are claimed.

### 12.3 Recommendation (proposed; pending operator disposition)

1. **Keep production cross-project transfer deferred** (#57 unscheduled). Do not implement export until the operator dispositions §14 and ADR-0023 P2's trusted channel design exists. This deferral is itself a valid research outcome.
2. When implementation is authorized, the **minimum boundary** is:
   - six conjunctive authorities;
   - C1 per-record-version, destination- and audience-bound, expiring X (C2 and C3 are optional operator-selected additions);
   - the E1 envelope with attribution minimization;
   - O1 fail-closed foreign reads with local continuation;
   - received content and relations held only in a federation-owned private store, never in canonical banks;
   - authority-version-vector keying plus a commit-time recheck for every derived artifact;
   - content-free markers;
   - the separate `derived-erasure-pending` state;
   - P default deny for foreign content;
   - private→public not supported initially.
3. Threat limits to state publicly: no recall of disclosed bytes, clones or Git history; no protection against a privileged host actor (ADR-0023:121-122); developer isolation no stronger than the OS account.

### 12.4 Explicitly not done

There is no implementation, schema, export engine, grant store or receipt
format. There is no real transfer, no production #57, no completed derived
erasure, and no coding-benefit claim.
