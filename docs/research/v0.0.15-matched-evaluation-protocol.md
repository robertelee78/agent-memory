## 3. Study architecture

### 3.1 Three layers, one unchanged primary meaning

1. **Primary study P (confirmatory once authorized).** Matched memory-on versus
   memory-off executable coding outcome. "On" means the normal eligible
   agent-memory integration with a prepared, source-bound project bank; "off"
   means no agent-memory skill, hook, bank or runtime state, and nothing else
   changed. This meaning MUST NOT change when mechanism studies are added. omp
   is the primary harness.
2. **Mechanism sub-studies M1–M4 (exploratory).** Variants of the *on*
   configuration, or offline retrieval-level runs with no agent, that isolate
   seeds, expansion, ranking and exposure. They never add memory to an off arm
   and never substitute retrieval scores for the P outcome.
3. **Stage program S0–S8.** Formation, retrieval, lifecycle, scope, adversarial,
   reproducibility and held-out-procedure obligations of ADR-0006, many as
   separately controlled non-coding cases.

### 3.2 Units

A *run* is one agent session on one task in one arm. A *pair* is the on and off
runs of one task × harness × repetition, sharing every input except memory
availability. Pairs nest in tasks; tasks nest in repositories. The primary
analysis unit is the task; the independent inference cluster is the repository
(§10).

### 4.4 Hidden oracle and grader

Per candidate, both solver trees MUST lack the oracle module
(`tests/contracts/test_project_identity.py`, `test_tombstones.py`,
`test_scope_policy.py` or `test_bank_usability.py`), every duplicate or
answer-bearing copy, this protocol and its data directory, and all Git history.
The solver tree is one orphan root commit of the sanitized tree, with no source
refs, packs, reflog, stash, notes, remote or access to the source object store.
Without that, the unseeded code in history is the answer. Every other
removed/rewritten path is listed with its blob (§4.3). A separately authored
non-revealing smoke test is added. If removal makes the task or oracle invalid,
the task is excluded; the oracle is never exposed and the full-module rule is
never relaxed.

The grader keeps the immutable base tree outside every solver namespace. After
the run it collects only the solver diff and applies it to a fresh copy of the
**original** tree (oracle, registry, bank restored by blob), never to the solver
tree. It runs, in a fresh `tests/world.py` `World()`:

```python
world.run([sys.executable, "-I", ROOT / "scripts/run_contract_suite.py", ROOT / oracle_module],
          check=False, timeout=300, group=True)
```

This is exactly the per-suite execution in `scripts/test_gate.py` `main()`.
No public single-suite CLI exists. The worker refuses paths outside `tests/`,
validates the World marker and HOME/XDG/client isolation through
`require_world()`, and prints one JSON counts line. The regression check uses
the same invocation per module, or the full `scripts/test.sh --release --json`
of the CI workflow where affordable.

**Exact pass** = worker return code 0; `counts.passed` true;
`counts.tests` equal to the manifest's expected count; zero failures, errors,
skips, expected failures and unexpected successes; every module in the task's
**baseline-green regression set** still passes; and no prohibited path changed
(oracle, grader, registry beyond the declared rewrite, CI, the bank). The
baseline-green set is the modules that pass at the clean base on the same
grader host and interpreter during qualification. The full gate is not green
at the pins: v0.0.14 recorded retained installer-suite failures and a stopped
exhaustive gate (`docs/research/2026-11-01-v014-qualification.md` lines 49–61),
and §4.2 observed two more failing modules. A module failing at base is
reported and never counted as a solver regression. Grading never returns
hidden test text to the solver. Infra timeout, crash or missing output is
`invalid`, never `fail`, `pass` or no-match.

## 5. Memory preparation and labels

Each task has a pre-task source snapshot and an on-arm bank manifest: exact
canonical bytes and sha256; project ID; admitted record IDs and versions;
lifecycle, trust, scope, conditions and applicability; origin and evidence;
timestamps; seeded candidate observations with their admission outcomes.
Records MUST be safe, project-scoped and grounded in earlier independent task
evidence. They MUST include relevant, irrelevant, stale, conflicting, revoked
and no-help cases, and MUST NOT contain the target fix, the reference patch,
the hidden oracle or its assertions.

Two labelers who did not author the task, the seed or the bank independently
label every record admissible/inadmissible and relevance-graded (0–3) per
task. Disagreements are adjudicated by a third person before any trial;
Cohen's κ is reported. Labels, hidden tests, reference patch and answer key stay
outside every solver world. A proposed reusable procedure carries an
applicability predicate and a held-out task/repository (S8); it stays
non-binding without separate promotion review (ADR-0006). Banks for private
repositories stay in access-controlled storage, with only hashes and a
sanitized description published.

## 6. Matched pairing, randomization and isolation

### 6.1 Pair construction and order

Each task × harness × repetition yields two fresh disposable worlds with
identical sanitized tree, visible tests, assignment, tools, network policy,
resource/token/time limits, harness version, model, provider and settings.
Run order within a pair is randomized and balanced: for each task × harness,
repetitions are blocked in twos (one on-first, one off-first), with the odd
remainder drawn by a seeded PRNG whose seed, algorithm and draws are
recorded before the first run. Pairs run back to back on the same host and
provider route to reduce provider drift. Concurrent lanes MUST NOT share a
writable state or a rate-limit bucket in a way that favors one arm.

### 6.2 Arm configuration per harness

Only agent-memory availability differs. Harness-native memory is a confound,
not "memory on". It MUST be held identically off in both arms, or the pair
recorded invalid (P7).

| Harness | On arm | Off arm | Held off in both arms (source) |
| --- | --- | --- | --- |
| omp (primary) | Pinned external agent-memory release; shared skill/CLI route discoverable at an omp skill root; #249 native extension only once delivered and selected via explicit `--presets … omp --omp-agent-dir …` (omp design) | No agent-memory skill, extension, hook, bank or state at any root below | `memory.backend: off` (default), `autolearn.enabled: false` (default), empty `<agent dir>/managed-skills` (discovered unconditionally), no Hindsight/Mnemopi env (`HINDSIGHT_*`), no skillshare lock, no advisor memory tools (omp docs `memory.md`, `settings.md`, `skills.md`, `config-usage.md`) |
| Codex | AM `codex` preset: `$CODEX_HOME/skills`, `$CODEX_HOME/AGENTS.md`, `$CODEX_HOME/hooks.json` | None of those AM entries | Any Codex-native memory/history feature of the chosen version, enumerated from that version's documentation at execution (unverified here) |
| Claude Code | AM `claude` preset: `$CLAUDE_CONFIG_DIR/skills`, `CLAUDE.md`, `settings.json` hooks | None | Claude-native memory features of the chosen version (unverified here) |
| OpenCode | AM `opencode` preset: `$XDG_CONFIG_HOME/opencode/skills`, `AGENTS.md`, `plugins/agent-memory.js` | None | OpenCode-native memory of the chosen version (unverified here) |

The AM install roots come from `installation.py` lines 415–443. The `all`
preset also writes `~/.agents/skills`. omp's skill providers include `native`
(`<ancestor>/.omp/skills`, `~/.omp/agent/skills`), `claude`, `agents`
(`.agent[s]/skills`), `codex`, `opencode`, `github` (`.github/skills`),
`omp-plugins`, `skillshare` and `omp-managed`. Project roots of foreign
providers load by default. Of the user roots, `.agent[s]` load by default, and
Claude's load once `CLAUDE_CONFIG_DIR` is set; other foreign user roots are
opt-in through `enabledProviders`. So another harness's AM installation in a
shared HOME can leak into omp. Every world therefore gets its own HOME, XDG roots,
`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, omp agent directory (`PI_CODING_AGENT_DIR`)
and credentials copy, as `tests/world.py` does for its own clients.

The off arm keeps ordinary repository instructions and non-memory tools. It
MUST NOT be made weaker by blanket `--no-skills`/`--no-context-files` unless the
on arm uses the same flags and receives agent-memory another way. Both arms
otherwise install no third-party skills.

### 6.3 Shared isolation controls

Fresh clone/reset per run; no shared writable state, conversation, session
store, cache or carried-over transcript; no access to the paired run, earlier
runs, baseline output, labels or grader. Provider-side memory, conversation
retention features and prompt caches are recorded; where a cache cannot be
disabled, cold/warm state is recorded per run and randomized order spreads it.
Network: model endpoint plus declared package mirrors only, identical in both
arms; the agent-memory release is installed from a pinned local artifact, not
fetched at run time. Fixed seeds and temperature are used where the provider
offers them, and nondeterminism is reported where it does not. Hooks/tools
needed for a fair configuration but unavailable make the pair `invalid`, never
an empty bank or a correct abstention.

### 6.4 Self-hosting isolation (agent-memory as task repository)

Observed facts at the pin: 21 committed `memory-bank/` files (an
agent-memory-format bank); the code under edit lives in
`skills/agent-memory/scripts/agent_memory/` (`scripts/*.py` are `runpy` shims
into it); 74 tracked test files reference `skills/agent-memory` by path;
`skills/agent-memory/SKILL.md` is the only tracked skill manifest; no tracked
`.omp/`, `.claude/`, `.codex/`, `.agents/`, `.opencode/`, `AGENTS.md` or
`CLAUDE.md`.

Both arms therefore start from one sanitized common snapshot:
`memory-bank/` and all history removed (§4.4), registry rewritten, and
`skills/agent-memory/**` **retained as inert product source** (P4). Removing
it would delete the code under edit and break the oracle's fixtures.
Neutralization means: identical bytes in both arms; not under any discovery
root of the harness (it sits at workspace `skills/`, which omp's documented
providers do not scan; the other harnesses are verified empirically by the
canary); no installed runtime, hook, binding or `skills.customDirectories`
entry points at it. The on arm activates only the **pinned external** release
installed outside the workspace, never the possibly regressed code being edited.
If any harness lists the workspace skill as loadable, self-hosted pairs on
that harness are invalid, or the task is excluded. Both arms can read
`SKILL.md` as ordinary source; that is product documentation, not project
memory, and it is identical across arms. This is a stated limitation of
self-hosted tasks, which are a separate analysis stratum.

### 6.5 Off-arm discovery canary

Per harness and world template, before any trial and after every configuration
change, inspect from inside the off world: accessible filesystem roots, Git
refs/objects (including packs and `lost-found`), HOME/XDG and every
client-specific root above, workspace discovery paths, environment, the
harness's own skill/tool/hook/extension listing, and permitted network for any
bank, skill or runtime artifact, including historical copies. Sensitivity
check: in a throwaway clone of the template, plant inert sentinel artifacts
(a bank-shaped directory, a skill named like agent-memory, a hook entry, a
history object) at each inspected route; the canary MUST detect every one.
Any found artifact, auto-load route or uninspectable route blocks the
template or marks its pairs invalid. Absence of a recall event is never proof
of cleanliness. The on arm is separately verified to load the pinned external
integration (listed skill, actual CLI resolution path and version).

and failure class. Retain: the safe raw event stream and tool calls; candidate
observations and admission decisions; exact bank bytes (or an encrypted
access-controlled snapshot); every retrieval request and result
ID/version/rank/scope/evidence/selection/exclusion; and **the exact
prompt-visible assembled context**, with source labels and byte and token
counts. Empty retrieval, no retrieval, retrieval failure and unavailable
telemetry are four distinct values. Retain the final diff, grader command,
environment, output and exit, plus hidden-oracle integrity hashes.

A selected-result list is not proof of what the model saw. The capture route
MUST read the actual request sent to the model: a sealed-world model-API
recording proxy, or the harness's own persisted request transcript where it
demonstrably contains the full request. The route is an execution prerequisite
per harness and per subscription terms (U11). #249's rule that AM's omp
extension never retains display text, thinking or tool payloads still holds:
evaluation capture happens at the sealed-world harness/provider boundary,
never through AM product code. A trial without exact visible-context capture
cannot support a benefit claim. Secrets are excluded; sensitive traces stay
private with public hashes and sanitized summaries.

### 8.2 Deviations, missingness and retries

Both attempted and evaluable denominators are reported for every metric. A
pair is evaluable only when both arms produced a graded outcome with no
protocol deviation. Infra failure of either arm (provider 5xx, harness crash
before the first model turn, grader crash) allows one rerun of the **whole
pair** with fresh worlds and the same order assignment, logged; a second
failure makes the pair invalid. Single-arm retries are prohibited. Broken
tests, discovered oracle exposure or a failed canary are deviations: the
affected pairs are invalid and, for oracle exposure, the task is excluded
across arms. The primary analysis adds worst-case and best-case bounds that
impute invalid pairs as (off-pass, on-fail) and (on-pass, off-fail). Every
deviation is recorded before outcomes are unblinded.

## 9. Mechanism sub-studies (ADR-0024 R5, ADR-0023 D1/D3)

### 9.1 Common rules

- Variants differ only in the named mechanism. Corpus, eligible set, query
  text, embedding profile, model, harness, tools and result/byte/token budgets
  are fixed and recorded.
- They run offline (M1–M3: no agent, retrieval-level) or as on-arm agent
  variants (M4). The P off arm is never modified or padded. The P outcome is
  never replaced by recall@k, hit@K, MRR or nDCG.
- Ground truth for relevance and relations is authored independently, before
  any graph or embedding output exists or is shown, by people who cannot see
  edges, similarity scores or candidate lists. It MUST NOT be derived from
  graph edges, `derived-from` links or similarity thresholds.
- All three use cases are covered: **coding** (executable oracle),
  **investigation** (a question about the repository with an independently
  authored answer key: required facts, forbidden claims, mandatory caveats;
  automated key-fact matching plus a blinded rubric for residual judgment),
  **orientation** (a fresh-session resume graded against a current-state
  checklist and a retired-guidance canary that must not appear, after the
  `test_bank_usability.py` `RETIRED_GUIDANCE_CANARY` pattern).
- Native qualification runs before semantic/graph ordering and before budgets
  (ADR-0024 R3). Unavailable semantic or graph service is `unavailable`, never
  a semantic no-match; literal fallback is labeled.
- Mechanism results form a separate exploratory family with no confirmatory
  claims (P8).

### 9.2 M1 — seed discovery: lexical/exact versus semantic

Arms: **L** native exact/path/literal retrieval; **S** semantic seed retrieval
through the configured embedding profile over the same eligible corpus. Same
query, same k, same budgets. Metrics: eligible-relevant recall@k, nDCG@k,
correct/false abstention, unsafe/inapplicable exposure (must be 0), latency,
embedding calls/tokens. Prespecified stratum: queries with no required
literal overlap. The labeled-recall baseline observed one such deliberate miss
in 17 authored relevance hits. That observation motivates this stratum and
says nothing about S.

### 9.3 M2 — graph expansion over identical seeds

Seeds are frozen per query, using two seed sources analyzed separately: the
realistic seeds output by M1-L, and oracle seeds (independently labeled
relevant records). Arms: **E0** no expansion; **Et** typed expansion via
ADR-0024 template (2) over typed relations (`corrects`, `supersedes`,
`derived-from`, evidence, condition, scope); **Eu** untyped expansion over the
same adjacency with types and provenance erased, i.e. uniform neighbor
expansion. Hop, added-node, byte and time budgets are equal. Metrics:
incremental relevant yield = new relevant records / budget used; new
irrelevant, unsafe, inapplicable or hidden-endpoint exposures; displacement of
mandatory caveats (must be 0, §9.6); propagation of seeded inaccurate relations
(§9.7).

### 9.4 M3 — ranking over an identical candidate union

For each query, U = union of all post-qualification candidates produced by L,
S, Et and Eu. Rankers: native order, semantic score, graph proximity, and a
seeded-random control, each applying the same final count and payload budget
after ranking (the R3 seam, not post-hoc sorting). Metrics: nDCG@k and MRR on
graded labels; budget-truncated relevant loss; mandatory-context retention.
Only order changes, so differences are attributable to ranking alone.

### 9.5 M4 — cue versus primary guidance versus optional pulls

On-arm agent variants, ADR-0023 D1: **C** cue only (no bodies); **P**
primary retrieval with mandatory caveats; **PX** primary plus bounded
related-memory pointers the agent may explicitly fetch. Record the actual
visible cue, guidance, caveat and related context, pointers offered and pulled,
bodies fetched, context bytes/tokens, latency and cost. Outcomes per use case
(exact pass, answer-key score, orientation checklist) and unsafe exposure. An
unfollowed pointer's body MUST be absent from context; the audit reports
violations. Total-effect reference for investigation/orientation uses
unpadded off runs (§11.1).

### 9.6 Mandatory-caveat controls

Labeled cases whose applicable guidance has an answer-changing condition,
correction, superseding version or unresolved contradiction (assembly conflict
groups, `test_assembly.py`). Metrics: caveat-in-primary rate = cases whose
mandatory caveat is visible with the primary guidance / labeled cases
(target 1.0); caveat-only-behind-pointer count (must be 0); correct explicit
budget/clarification outcome when guidance plus caveat cannot fit; downstream
harm when a caveat is missing. Caveats never reveal inapplicable or unsafe bodies.

### 9.7 Relation truth and inaccurate-relation controls

An independent relation suite of (a, b, type, truth) triples with truth in
{true typed relation, unrelated, plausible-but-wrong}, double-labeled with κ
reported. Controls: (i) plausible-but-wrong *inferred* suggestions, which must
render as inferred with model/generation provenance and never as verified
(count presented-as-verified; target 0); (ii) agent acceptance rate = outputs
asserting a wrong suggested relation as fact / wrong suggestions shown;
(iii) relations whose endpoint is hidden or inapplicable, where label, path,
count or body must not leak (target 0); (iv) wrong *recorded* relations are
canonical poisoning and belong to S6 with inert fixtures. Similarity never
establishes correction, supersession, causality, applicability, trust or
absence (ADR-0023 D3).

### 9.8 Prerequisites

M1–M3 need #255 G1's qualified scratch pipeline or the v0.0.16 G2/G3 runtime,
with its frozen paraphrase/relationship suites and resource tolerances. M4
needs P1 (v0.0.16) and, for omp native cues, #249's extension points. None is
available at this pin. These are execution prerequisites, not blockers to this
protocol. Image, license and platform conclusions belong to #255's
qualification and are not restated here.

## 10. Analysis

### 10.1 Estimands

For harness h, held-out task t with R_t evaluable repetitions:
d̄_{h,t} = (1/R_t) Σ_r (Y^on_{h,t,r} − Y^off_{h,t,r}), Y ∈ {0,1} exact pass.
Primary: θ_omp = (1/T) Σ_t d̄_{omp,t}, task-weighted, with repository clustering
retained. Secondaries: θ_codex, θ_claude, θ_opencode, defined the same way,
with Holm family-wise adjustment across the three. Everything else (S1–S8
metrics, M1–M4, cross-harness contrasts) is exploratory.

### 10.2 Inference valid for few clusters

Primary test: exact repository-level sign-flip randomization test of
H0: repository totals Σ_{t∈g} d̄_t are symmetric about 0. The sharp null that
memory availability does not change any run's outcome distribution, with
randomized order and otherwise identical conditions, implies this. All
tasks of a repository flip together. The p-value counts all 2^G patterns.
Confidence interval: inversion of the shifted test, reported with its
symmetric-shift assumption. A task-level sign-flip test, valid only for the
finite set of studied tasks, is reported as supplementary and never as
population generalization. Ordinary bootstrap with few clusters and McNemar
over correlated pairs are not used.

Arithmetic limit (observed by exact enumeration in the calculation sheet): the
smallest attainable two-sided p is 2/2^G.

| Repositories G | 3 | 4 | 5 | 6 | 7 | 8 | 10 | 12 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| min p | 0.25 | 0.125 | 0.0625 | 0.03125 | 0.0156 | 0.0078 | 0.0020 | 0.0005 |

So the plan's illustrative "≥5 repositories" floor **cannot** reject at
α = 0.05 at all; G ≥ 6 is needed for the primary test, and G ≥ 7 for Holm's
first secondary threshold (0.05/3 ≈ 0.0167). Proposal P2: confirmatory
requires G ≥ 8 independent repositories. With fewer, results are descriptive
or inconclusive. The pilot (G ≥ 3) is descriptive only.

### 10.3 Stopping and blinding

Fixed sample: no interim efficacy look, no extension after seeing outcomes.
Pause/stop rules (thresholds are operator choices U7; proposals in brackets):
any S5 leak or S6 objective achieved outside a sealed world stops the study
[zero tolerance]; a failed discovery canary stops that harness template; a
harness with more than [20%] invalid pairs stops and is reported; reaching the
budget cap stops with attempted/evaluable counts. Grading is automated; human
labelers and rubric graders are blind to arm; analysis code and thresholds are
frozen and hashed before unblinding; arm labels are coded.

## 12. Confounders, limitations and risks

- **Answer leakage** through authors, history, this protocol, overlapping visible
  tests (P5) or memory: separate authors and labelers, orphan history, removal
  lists, banks reviewed against the reference patch.
- **Context and tooling differences**: on adds context and tools by design.
  Total effect is the P estimand; mechanism attribution belongs to M1–M4; total
  visible context is recorded per run.
- **Model nondeterminism, provider revisions, rate limits, caching**: pinned
  where possible, randomized order, adjacent pair execution, settings and
  outages recorded.
- **Training contamination and shared history**, especially for public
  repositories and this repository: provenance/date audit, held-out
  repositories, explicit limitation.
- **Self-hosting**: both arms can read agent-memory's own documentation (§6.4);
  separate stratum.
- **Learning across runs**: fresh worlds, no shared session stores.
- **Unequal client capability and instrumentation**: within-harness comparison
  first; missing capture is reported and blocks benefit claims for that harness.
- **OpenCode**: the documented short control-pass acknowledgment text
  (`2026-10-28-v009-opencode-native.md` lines 102 and 138) can add visible
  output in on runs. It is captured and stratified; the removed silence
  experiment is not restored, and full silence is out of scope.
- **Adversarial fixtures** live only in disposable sealed worlds.
- **Selection and cost bias**: every attempt and missing client is reported;
  unaffordable stages are reported deferred, never silently dropped.
- **Private data**: restricted evidence, sanitized publication, no secrets.
- **Baseline gate not green at the pins** (§4.4): per-task baseline-green sets
  are required.
