### Current implementation findings

All paths below are relative to the repository root. Product modules are under
`skills/agent-memory/scripts/agent_memory/`.

- `client_hooks.parse` accepts bounded UTF-8 unique-key JSON objects, rejecting
  duplicate keys using `frontmatter.unique_object`. It validates the hooks object
  and prompt event list; it does not currently validate a present Stop event's
  list shape. Empty bytes are accepted for fresh-install merge initialization.
- `client_hooks.locate` compares complete receipt groups, requiring exactly one
  match. It rejects a receipt group without exactly the `hooks` outer key, but
  does not validate the nested receipt list. Python equality alone also regards
  JSON `true` and `1` as equal; meaningful adapter flags must not inherit that
  equivalence. Matching cannot be reduced to command/path substrings.
- `installation.verify_targets` calls `trust_paths.tree`, fingerprints the target,
  then parses/locates receipt-owned prompt and an optional truthy Stop group for
  hook-config targets. It finally fingerprints again. Other targets retain exact
  identities, artifact checks, and the existing managed-source qualification.
- `diagnostics.runtime_doctor` already holds an existing shared lifecycle lock and
  checks receipt/journal stability. Its target loop checks activation blocks by
  sentinel/hash but whole-file-compares hook-config targets. That is the mismatch.
- `installation.prepare.add` merges owned prompt/Stop groups. It needs to consume
  the common evaluator when a previous hook receipt exists; fresh installation
  still uses collision-aware `merge` without adopting any unowned lookalike.
- `uninstallation.prepare.inspect` independently removes recorded groups and
  preserves changed groups. It must also consume the same evaluator before
  removal; otherwise the all-paths requirement is incomplete. Its existing
  whole-document comparison to a backup is a restoration guard, not a health
  check, and remains strict.
- `updating.ownership`, update no-op verification, install readback/recovery, and
  `doctor_fix.runtime` already delegate to `installation.verify_targets`; these
  acquire the common policy transitively. No new repair authority is added.
- `installation.client_hook_entries` records both prompt and Stop entries;
  Claude Stop records `asyncRewake: true`. Older prompt-only receipts have a
  separate existing migration diagnostic. OpenCode uses `hook-link`, not JSON.
- `trust_paths` checks Unix ownership, ancestor safety, ordinary node types and
  modes. These checks do not authenticate already-loaded code or audit ACLs.

The language-server references request reported no language server available.
The caller inventory above comes from source inspection, not executed checks.

## High-level design

Keep ownership policy with the lifecycle owner, in `installation.py`; no new
module, receipt schema, dependency, executable hook discovery, or public command
is needed. Add one common non-mutating filesystem evaluator:

```python
def verify_hook_target(target):
    # Return an internal observation only after all ownership and stability checks.
    return {
        'scope': 'receipt-owned-entries',
        'identity': observed,
        'raw': raw,
        'document': document,
    }
```

`target` is one existing receipt-shaped `hook-config` target: absolute canonical
`path`, file `identity` with recorded mode, required complete `hook_entry`, and
optional complete `stop_entry`. The function raises existing `ContractError` or
`TrustPathError`/filesystem failures, never returns a successful partial result.
It performs no write, lock creation, repair, receipt mutation or JSON re-encoding.
`raw` and `document` are internal observations and MUST NOT be added to public
diagnostic results, logs or receipts. The observed fingerprint is current source
stability/transaction evidence, not equality with historical shared-file bytes.

`installation.verify_targets`, doctor, prior-install planning and uninstall
planning MUST call this evaluator for hook-config ownership. `merge` and `remove`
remain mutation builders using the same `parse`/`locate` primitives, not competing
health evaluators. Whole-file equality remains mandatory for transaction inputs,
staged outputs, backup identity, activation readback, rollback and receipt/journal
integrity.

Activation remains its existing sentinel-block policy; this task does not create
a new generalized ownership framework or change other target-kind policies.

## Low-level design

### JSON and receipt matching (`client_hooks.py`)

1. Keep `MAX_CONFIG = 1024 * 1024`, duplicate-key rejection at every JSON object,
   UTF-8 rejection and the root/hooks object requirements. Validate a present
   `Stop` event as a list as well as `UserPromptSubmit`. Unknown top-level keys,
   unknown events, unrelated valid groups and key order/whitespace are preserved
   and are not ownership evidence.
2. Keep `locate(document, owned, event=EVENT)` as the single exact-match primitive.
   Validate the requested event list, including Stop, before iterating it.
   Validate that recorded ownership is a nonempty `hooks` list of command
   dictionaries with nonempty bounded command strings and `type == 'command'`.
   Preserve and compare every recorded nested key/flag; do not regenerate the
   expected group from the current install path or strip unknown fields.
3. Use JSON-type-sensitive structural equality for complete groups. Canonical
   unique-key JSON encoding of candidate and receipt groups is sufficient;
   dictionary order is immaterial, list order is material, and booleans, strings
   and numbers are not interchangeable. Only candidate groups with the supported
   group structure can match. In particular deleting/changing `asyncRewake`,
   changing `type`, or substituting `1` for `true` must not match.
4. Require exactly one match for each recorded event. Missing, changed and
   duplicate groups remain ownership failures. Preserve the existing public
   grouping of these cases where absence and modification cannot be distinguished
   without guessing ownership. Malformed/duplicate-key JSON, invalid receipt,
   unsafe path/mode, and concurrent change retain separate failure paths rather
   than being downgraded to benign unrelated edits.
5. A present but null/empty/malformed `stop_entry` is invalid evidence, not an
   omitted optional group. Test field presence rather than truthiness in the
   common evaluator. An absent Stop receipt does not authorize adopting or
   certifying a current Stop lookalike.

### Stable filesystem observation (`installation.verify_hook_target`)

The evaluator executes these steps in order:

1. Require kind `hook-config`, canonical absolute path without traversal, a file
   receipt identity with valid recorded permission mode, and sufficient prompt
   ownership evidence. A legacy target lacking `hook_entry` is explicitly
   unverified/migration-pending; historical hash equality cannot certify it.
2. Apply existing `trust_paths` ordinary-path/owner/ancestor checks. Require the
   target to be a regular file, not a symlink, directory, FIFO, socket or device.
   Reject unsafe paths before reading them. Do not resolve a mutable ancestor
   symlink away to make it appear canonical.
3. Take the current file fingerprint. Require current file mode to equal the
   recorded mode in addition to current Unix path-trust checks. This retains
   doctor's existing mode refusal while allowing only shared-document bytes to
   differ. Do not require the historical whole-file hash to match.
4. Read bounded bytes (at most `MAX_CONFIG + 1`), require the JSON bound, call
   `client_hooks.parse`, then `client_hooks.locate` for the required prompt and
   every recorded Stop group. Blank/empty existing files cannot become healthy
   by using the fresh-merge empty-document behavior: the required group is absent.
5. Reapply path trust and compare the final full fingerprint with the current
   observation from step 3. A changed byte, mode or kind is a concurrent-change
   failure even if owned entries themselves remain exact. Return only after this
   check. Retain the existing fingerprint-based stability guarantee; this is not
   a claim of kernel-atomic snapshots or detection of arbitrary change-and-restore
   events wholly between observations.

Use existing `require`, `fingerprint` and `trust_paths` patterns. No raised file
bounds or relaxed identity checks. Whole-file fingerprints still include modes
and current bytes; only comparison with the old receipt hash is removed for
shared hook health.

### Exact caller migration

| Caller | Change | Boundary retained |
| --- | --- | --- |
| `installation.verify_targets` | Branch on **every** hook-config, call `verify_hook_target`, continue; remove its duplicate parse/locate code and legacy whole-file fallback. | Existing list return of managed-source qualifications and all non-JSON target verification. |
| `diagnostics.runtime_doctor.check_target` | Add hook-config branch calling the evaluator, before the generic exact-fingerprint branch. | Shared lock, receipt/journal final check, wrapper executable check, client artifact digest, permissions and failure redaction. |
| `installation.prepare.add` hook-config | For a previous owned target, evaluate it and use its returned raw/document; require its observation to equal the planner's `before` fingerprint. Fresh install still parses original bytes and uses collision-aware merge. | Existing explicit `repair_missing_hooks` boundary for a wholly absent target; do not extend it to changed or insufficient receipt evidence. Before/after/backup hashes and journals remain exact. |
| `uninstallation.prepare.inspect` hook-config | Evaluate before removing groups; use returned raw and current identity, require agreement with `before`; preserve the target on failure using the existing preservation result. | Only exact recorded groups removed; unrelated JSON retained; exact-original-backup restoration guard remains unchanged. |
| `updating`, `doctor_fix`, install/recovery readback | No second evaluator; keep their calls to `verify_targets`. | Existing repair transactions, outside-helper policy and interrupted evidence. |

The small `uninstallation.py` change is a necessary integration point for the
all-paths requirement and must be explicitly included in implementation approval;
it is not bank work. The parent reserves its #245 edits to `diagnostics.py` until
this task hands off the runtime-target block.

For doctor, retain component `runtime.target.hook-config`. Extend the existing
`Report.add` result pattern only as necessary to expose verification scope in a
structured, bounded way; the intended per-check additive field is
`verification_scope: 'receipt-owned-entries'`. If `Report.add` does not accept
arbitrary fields, attach this field to the just-created check through the existing
report representation within the target block rather than widening unrelated
report interfaces. Detail text explicitly says receipt-owned prompt/recorded Stop
entries, not whole-document identity. A healthy check produces no routine warning
solely for unrelated JSON drift. Never expose command text or raw JSON.

### Preservation and ownership cases

| Case | Required outcome |
| --- | --- |
| Add unrelated valid root key, another prompt/Stop group, or another event | Healthy owned-entry check, no drift-only warning, no config/receipt write. |
| Reformat/reorder JSON keys, retain complete exact groups | Same healthy scope; original bytes stay untouched. |
| Remove/duplicate/change a recorded prompt or Stop group | Failure; uninstall preserves it and source references; no adoption. |
| Change command/type/adapter flag, including boolean to number | Failure based on full group equality, even if the command still mentions the owned path. |
| Duplicate key at root or nested group; invalid UTF-8/JSON/root/event shape | Failure before ownership can be certified; original bytes preserved. |
| Symlink/nonordinary target or unsafe ancestor/owner | Trust/type failure; never parse through it. |
| Current mode differs from receipt | Failure, including when JSON ownership entries are unchanged. |
| Byte/mode/path change during observation | Concurrent-change failure; never update receipt to bless it. |
| Legacy hook-config lacks sufficient prompt evidence | Unverified failure, bounded migration/reconciliation guidance; no historical hash fallback. |
| Valid prompt-only legacy receipt | Verify only recorded prompt ownership; existing hook-migration warning remains; no inferred Stop ownership. |
| Activation outside text edited | Existing managed sentinel-block health and preservation remain. Missing/duplicate/modified block still fails. |
| OpenCode plugin link redirected | Exact `hook-link` identity failure, never routed to JSON evaluator. |
| Wrapper, signed source, client copy/link or mode drift | Existing exact identity/artifact/signature refusal remains. |
| Interrupted journal or active writer | Existing recovery/deferred checks remain; doctor neither resumes nor clears evidence. |

## Regression tests and bounded acceptance

Reuse registered suites rather than create a second harness:

- `tests/contracts/test_runtime_diagnostics.py`: real public installed/outside
  doctor for both Codex and Claude; unrelated key/group and formatting positives;
  exact byte/mode preservation; prompt/Stop removal, duplication and full-group
  modification; type/flag changes; duplicate-key and malformed JSON; legacy
  insufficient receipts; unsafe nodes and mode drift; OpenCode plugin link and
  existing wrapper/copy/link strictness. Receipt alterations for legacy fixtures
  must also keep the completed journal's receipt identity coherent so the test
  exercises insufficient ownership evidence rather than merely journal mismatch.
- `tests/contracts/test_client_hooks.py`: focused supported-shape, nested receipt,
  duplicate-key and JSON-type-sensitive equality controls supplement public tests;
  they do not replace public acceptance.
- `tests/contracts/test_runtime_uninstall.py` and/or existing installer tests:
  prove preview/removal preserves unrelated keys/groups, refuses or preserves
  changed/ambiguous groups, and install/update/readback use the common evaluator.
  Do not assert source text, implementation strings or new diagnostic prose.
- Existing signed-source, lifecycle-trust and doctor-fix suites remain mandatory
  strictness controls; do not weaken or rewrite existing checks to make this pass.

For deterministic racing edits, use the existing isolated-World fault rendezvous
pattern, with one bounded `hook-ownership-before-recheck` fault point between
ownership matching and the final fingerprint. `fault` is already imported in
`installation.py`; only a validated disposable test World can enable it. The
external test controller waits for `.ready`, changes the config, then writes
`.release`. Doctor must fail even if the change only adds another unrelated key,
and preserve the controller's new bytes and unchanged receipt. Test rendezvous
files are explicit controller artifacts, not product repair writes; compare all
other state exactly. Test byte and mode races separately; the path/type negative
cases must never block on FIFOs. The failpoint has no effect in ordinary runtime.
