# #248 — Matched memory-on/off evaluation research execution plan

Work key: `robertelee78/agent-memory:ADR-0006:matched-evaluation-research`. Delivery: reviewed protocol in published v0.0.15. **Designing; proposed execution plan, not approval, implementation, experimental results or evidence of benefit.** Independent Opus design review and explicit operator approval precede starting; parent owns tracker. A later separate decision is required to build a harness and execute the full evaluation program.

## Why / What

Functional correctness, recall and anecdotes cannot establish causal coding benefit. Define a reproducible, practical, source-bound study comparing matched memory-on and memory-off coding runs with executable outcome tests, traceable inputs/context, safety controls and cost estimates. Produce a reviewed protocol suitable for a later harness/execution decision; do not claim improvement from designing it. The protocol must include omp (Oh My Pi) as an equal primary harness alongside Codex and Claude Code, retaining OpenCode and all ADR-0006 obligations.

## How / ordered research work / outputs

1. **Trace obligations and pre-register the study.** Construct an AC-to-protocol matrix and the ADR stage map below. The observational unit is a matched pair; repeated pairs are nested within task and tasks within repository. Specify the primary harness-specific task-level estimand, independent cluster, valid inferential method, multiplicity, failure handling and stopping rules before any future outcome run. Separate feasibility/pilot from confirmatory decisions; operator approves material parameters before later execution.
2. **Specify a real executable task bank and labels.** Select immutable, redistributable source revisions with independently reproducible setup and independently held tests. Candidates grounded in the pinned repository, to be turned into bounded real coding assignments by a later authorized harness task:
   - **Identity:** modify a deliberately seeded regression so a moved no-remote checkout preserves the existing project ID and records explicit alias history; hidden oracle derived from `ProjectIdentityContract.test_no_remote_move_keeps_id_and_preserves_location_history` in `tests/contracts/test_project_identity.py`.
   - **Deletion:** repair a deliberately seeded projection-rebuild regression so an existing tombstone suppresses a deleted record despite changed conditions; oracle derived from `TombstonesContract.test_delete_rebuild_and_repeat_cannot_resurrect_id_under_changed_conditions` in `tests/contracts/test_tombstones.py`.
   - **Scope:** repair a deliberately seeded condition-matching regression so missing task/branch/component evidence never broadens guidance; oracle derived from `ScopePolicyContract.test_all_conditions_must_match_and_missing_context_never_becomes_universal` in `tests/contracts/test_scope_policy.py`.
   - **Local independence:** repair a deliberately seeded assumption that generated state is required for a fresh-clone bank; oracle derived from `BankUsabilityContract.test_fresh_clone_resumes_from_bounded_current_markdown_without_any_generated_state` in `tests/contracts/test_bank_usability.py`.
   For each future task manifest require pinned base commit, deterministic bug patch and fixture hash, assignment text, environment and setup commands, visible smoke test and separate hidden full-module/regression test invocation using the repository's actual test runner. Verify the seeded base fails the intended test and a separately authored reference repair passes the complete module before inclusion; those are future study qualification steps, not executed in #248. Prevent solver access to hidden tests/reference patches and prior answer-bearing history; retain enough non-secret source for ordinary real work. No invented exact command is asserted here; the later task author resolves it from the pinned runner and records it. Expand beyond this one repository with suitably licensed, pre-existing real coding tasks; stratify by repository and task family, complexity and available prior learning. Avoid equating a synthetic regression in this repository with representative field performance.
   **Hidden-oracle boundary:** For the four candidates the manifest must explicitly remove from both solver trees, respectively, `tests/contracts/test_project_identity.py`, `tests/contracts/test_tombstones.py`, `tests/contracts/test_scope_policy.py`, or `tests/contracts/test_bank_usability.py`, including any duplicate/answer-bearing copies and Git-history access to those files. List and hash every additional removed or altered test, fixture, reference patch and history path; provide a separately authored non-revealing smoke test. Keep immutable original full module and necessary fixtures in an external grader unavailable to the agent, then restore them only in a separate grading copy after collecting the solver diff, and run the original full module and hidden regression tests there using the pinned runner. Grading must not return hidden test contents to the solver. Record grader revision, integrity hashes and exact command/exit; verify seeded failure and reference-repair full-module pass before inclusion. If removal prevents a valid task or oracle, exclude it rather than expose the oracle or relax the full-module requirement.
3. **Define memory preparation and labels.** For each task specify a pre-task source snapshot and memory-on bank manifest with exact canonical bytes/hash, project ID, admitted record IDs/versions, lifecycle/trust/scope/applicability, origin/evidence, timestamps and seeded candidate observations. Use only safe project-scoped memories grounded in earlier independent task evidence; include relevant, irrelevant, stale, conflicting, revoked and no-help cases. Independently label admissible versus inadmissible records and relevant versus nonrelevant records before trials; hold out labels, hidden tests, reference patch and evaluation answer from agent. Do not place the target fix or hidden oracle in memory. Define applicability predicate and held-out task/repository for any proposed reusable procedure; it remains non-binding absent separate promotion review. Capture the exact memory snapshot and every candidate/admission outcome without publishing sensitive source data.
4. **Matched on/off and isolation.** For each task × harness/model × independent repetition, create two isolated disposable workspaces/homes/identities, with identical pinned repo/test/initial filesystem, assignment, available tools, network policy, resource/token/time limits and model/provider settings; pair and randomize execution order with recorded seed, balancing orders. Only memory availability differs: on uses the normal eligible skill/CLI/hook configuration and source-bound project bank; off disables all agent-memory skills, automatic hooks, bank mounts, runtime caches, carryover/transcripts and provider-side memory while preserving ordinary repository instructions and non-memory tool capability. Neither arm sees answer-bearing task history, baseline output, hidden oracle or paired trajectory. Record exact shim/config, HOME/XDG, source tree/index status and network controls; test visibility with canaries. A tool/hook needed for a fair configuration but not available must be reported as unavailable/invalid rather than treated as an empty bank or successful abstention. Fresh clone/reset between arms and repetitions, no shared writable state or conversation; fixed seeds where supported and report provider nondeterminism where not. Preserve identical test environment and independent hidden judge outside solver workspace.
   **Self-hosting isolation prerequisite:** For every repository shipping an agent-memory-format bank or auto-loadable memory files, construct one sanitized common source snapshot and Git history before pairing: remove or neutralize all committed banks, historical bank objects/refs, answer-bearing history and auto-discovered agent-memory skills/configurations from both arms, including workspace `skills/` and harness-specific discovery directories. Record source-to-sanitized transformation and hashes and verify both arms start with identical sanitized task code and visible tests. On receives only its prepared labeled project bank through the normal intended integration; off receives no bank or skill. Use a pinned, externally installed identical release of memory runtime, skill and hooks outside the solver workspace, never the potentially regressed code being edited; on alone activates that external integration while off cannot discover or invoke it. Per harness, before any trial, an off-arm discovery canary must inspect accessible filesystem, Git refs/objects, HOME/XDG, workspace/client discovery paths, environment, tool/hook/skill listings and permitted network for bank/skill artifacts, including historical copies. Use seeded inert sentinel artifacts to test the canary's sensitivity without exposing protected content. Block or classify the pair invalid if a bank, skill, auto-load route or inaccessible inspection is found; never call it clean because no recall event was observed. Verify the on arm actually uses the pinned external integration, and retain evidence of matching sanitized roots and the canary results.
5. **Record full observable pathway.** For every run bind task/fixture/source hashes; model/provider/model revision, temperature/seed if offered, prompt/system and allowed tools, harness version/adapter and invocation, OS/hardware, runtime/library versions, start/end, timeout/exit and failure classification. Retain safe raw event stream, tool calls, candidate observations, admission decisions, exact bank bytes or encrypted access-controlled snapshot, all retrieved result IDs/versions/ranks/scope/evidence/selection and exclusions, and the exact prompt-visible assembled context with source labels and byte/token counts. Record an explicit empty retrieval, no retrieval, retrieval failure and unavailable telemetry separately. Preserve final diff, test command/environment/output/exit and integrity of hidden oracle; exclude secrets and store sensitive traces privately with hashes and sanitized public evidence. A selected-result list is not proof of what the model actually saw. If exact prompt-visible context cannot be captured, mark the trial unable to support a benefit claim, rather than substituting intended context.

## Metrics, denominators and obligation stage map

| Stage | Proposed metric and collection/oracle | ADR-0006 obligation |
| --- | --- | --- |
| S0: structural and isolation qualification | Fixed canaries for structure, lifecycle, same-project scope, deletion/non-resurrection and poisoning; count pass/fail/not-run, not just pass percentage. Canary leak is a safety event independent of task success. | First-release structural, lifecycle, isolation, deletion, poisoning controls; do not imply newly run here. |
| S1: formation/admission | Independently labeled eligible relevant candidate set: precision = true eligible admissions / all admissions; recall = true eligible admissions / all labeled eligible candidates; record TP/FP/FN, abstentions/unavailable and zero-denominator as N/A. | Admission precision/recall; candidates and evidence retained. |
| S2: retrieval/assembly | Recall@k = relevant qualified records in top k / all labeled relevant qualified records; use fixed k and report coverage, hits and N/A denominators. Ranking use MRR and nDCG@k against graded independent labels. Abstention: correct-empty / labeled no-qualified-match cases and false-abstention / cases with qualified matches; separately report unavailable/invalid. Audit exact returned vs prompt-visible context, applicability and source safety. | Retrieval recall, ranking quality and abstention. |
| S3: matched task solve | Binary full executable-test resolution; report pair-weighted descriptive delta = (on-pass/off-fail − off-pass/on-fail) / evaluable pairs separately from the task-weighted primary estimand below. For seeded repeated failure, count recurrence of independently defined failure signature / opportunities where signature was previously observed, comparing paired rates; do not substitute raw steps or unique failures. | Executable task resolution; repeated-failure avoidance. |
| S3 resources | Count agent tool/action steps using a predeclared event taxonomy; provider-reported input/output and cached tokens, model-native tokenizer only where measured; elapsed wall time and optionally CPU; incremental canonical + generated bytes and records before/after, including peak and retained. Report distributions and unavailable telemetry, separate model thinking vs tool time when timestamps allow. | Steps, tokens, latency, storage growth. |
| S4: lifecycle | In labeled corrections/update cases, correct current version selected / applicable update cases, plus stale guidance exposure count; selective-forgetting precision = correctly withheld deleted/revoked items / all withheld items, recall = correctly withheld deleted/revoked items / all labeled items requiring withholding; check valid unrelated memories retained, no resurrection after rebuild. | Correct knowledge updates and selective forgetting. |
| S5: attribution/scope | Leak rate = unauthorized project-content disclosures / isolated cross-project attempts, plus absolute events and affected surfaces; misattribution rate = records credited to wrong developer / records with independently known originating developer. Unknown ground truth is N/A, never guessed. Disclose metadata and body separately. | Cross-project leakage and incorrect developer attribution. Synthetic, isolated separate repositories only; no actual federation transfer or assertion federation exists. |
| S6: adversarial | Count attacker objective achieved, rejected, inconclusive and exposures for content, evidence, scope, selection and consolidation-path poisoning. Cover stale facts, malicious repo documents, poisoned tool output, conflicting requirements, deleted data, ambiguous repository identities and hostile memory files; test each formation and use interface separately with safe inert canaries. | Full adversarial obligation, not just retrieval of a malicious string. |
| S7: client reproducibility | Run equivalent task/fixture/protocol matrix on omp, Codex, Claude Code and OpenCode; record invocation differences and completion, observable context, settings, refusal and missing instrumentation. Compare same-harness matched arms first; cross-harness results descriptive, not presumed identical. OpenCode's documented short control-pass acknowledgment-text limitation can affect visible output: capture and stratify it as a confound, without attempting to restore the removed silence experiment or expand scope to full silence. Source: `docs/research/2026-10-28-v009-opencode-native.md` at the pin. | Codex/Claude/OpenCode adapter reproducibility plus operator-required omp peer coverage. |

These stages are a proposed later program; protocol coverage does not assert stages were executed. Treat unobservable attribution, costs, tokenization, leak tests, instrumentation or harnesses as missing with reason, not zero. Some lifecycle/security experiments are separately controlled cases rather than coding-task outcome trials. A theoretical future federation-specific test requires an independent authorization/feature decision; current leakage controls only verify isolated project boundaries.

## Proposed sampling, analysis, costs and confounders

**Pilot, budgeted proposal:** 12 distinct tasks across at least 3 repositories and 3 families, one matched pair each per harness, plus two additional matched repetitions on four preselected tasks per harness: 48 + 32 = 80 pairs / 160 agent runs. Randomize pair order. Include the four pinned candidate families above as provisional inputs, with at least two other independently sourced repositories. Repeated subset informs within-task variability but is too small to establish benefit or reliable repository-cluster variance; report that limit and do not claim pilot power. Report unavailable clients rather than silently dropping them.

**Confirmatory proposal, subject to pre-run power/budget decision:** 60 held-out tasks across at least 5 repositories, 3 independent repetitions per task and all 4 harnesses = 720 pairs / 1,440 agent runs. Split by repository and task family before authoring examples; keep a held-out repository/task set for promoted-procedure generalization. Five repositories are an illustrative floor for corpus diversity, not sufficient justification for clustered inference. Use repeated-pilot data and operator's minimum meaningful effect for a simulation or other predeclared power calculation respecting task and repository dependence, and select a justified cluster count/method or label results exploratory before unblinding; do not silently remove required stages if unaffordable.

**Comparison:** The proposed primary estimand is the mean, across held-out tasks, of each task's average paired on-minus-off executable-pass difference across independent repetitions for **omp**, with repository clustering retained; each task, not each repeated pair, is the analysis unit. Codex, Claude Code and OpenCode are prespecified peer-harness secondary estimands with the same within-harness aggregation; predeclare Holm family-wise adjustment for their three comparisons, and treat other metrics as exploratory. The protocol must choose and justify before execution a confidence interval and hypothesis method valid for the actual number of independent repositories and nested task/repetition dependence, set a defensible minimum independent-cluster count or justify a suitable few-cluster method, and document simulations/power and assumptions. Five-cluster ordinary bootstrap and exact McNemar on all correlated pairs are not valid default shortcuts. If assumptions or required clusters cannot be met, report descriptive/inconclusive results, not confirmatory significance. Report task/repository/harness breakdowns, discordant pair counts, uncertainty, invalid and missing pairs; no improvement claim without matched baseline, actual memory bytes, prompt-visible retrieved context and executable outcomes.

**Budget worksheet, illustrative assumptions not measured:** 10 minutes and cumulative 120,000 input + 20,000 output tokens per multi-turn run at placeholder rates $3/million input and $15/million output imply $0.66/run. With repeated pilot above, 160 runs imply 22.4M tokens, $105.60 and 1,600 serial minutes; 1,440 confirmatory runs imply 201.6M tokens, $950.40 and 14,400 serial minutes. These are arithmetic illustrations, not realistic or measured ceilings. Measure cumulative per-turn input including resent context, output, cache reads and cache writes separately by client/model during the pilot; apply dated provider-specific rates and distinguish API metering from Codex/Claude subscription pricing, quotas and marginal or allocated costs. Model at least 0.5×–10× cumulative token/time scenarios, including warm/cold cache variations, concurrency/rate limits, retries, stage controls, fixture qualification, human review, storage and fees; use available telemetry, not guessed token conversions. Replace placeholders with pilot-measured distributions and actual pricing/entitlement before operator approves any study budget cap; if unmeasurable, report costs unavailable and require explicit disposition. Calculate storage from measured bytes/run and retention.

**Confounders / mitigation:** task and memory authors may leak answer/reference fix or provenance to solvers (blind held-out tests and independent labeling); context length and extra tooling can differ (record total prompt/context and distinguish total effect from mechanism, do not pad with answer-bearing data); nondeterministic models, provider revision, rate limits and caching affect pairs (pin where possible, randomize order, record settings and outages); training contamination and shared repo history (time/source audit, held-out repositories, explicit limitation); repeated attempts can learn across arms (fresh isolated sessions/homes and randomized order); adversarial controls can poison production (inert fixtures and disposable sealed worlds); cost/selection bias and unusable clients (report all attempts and missingness); private data (restricted evidence and sanitized release). Record changes/deviations before looking at outcomes.
