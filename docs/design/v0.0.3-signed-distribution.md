## Reuse the shipped pattern

Follow C2E: pinned Ed25519 public key, signed release manifest, verification before
candidate execution, staged activation and preservation-first uninstall. Retain
AWA's portable skill layout and short commands. Vox's Apple signatures concern
its native macOS product; AM needs C2E's cross-platform boundary. IOA Brain's
release-lifecycle-overengineering RCA reinforces one publishing transaction,
without qualification releases or manual assemble/sign/tag/draft choreography.

The public journey stays the existing one-line installer, `am --version`,
`am update`, and `am uninstall`. One publisher command owns packaging, signing,
publication and remote readback. Qualification runs locally on macOS/Linux in
isolated homes; do not add expensive hosted CI gates.

## Release assets and verification

Publish four assets: `agent-memory.tar.gz`, `release-manifest.json`,
`release-manifest.json.sshsig`, and rendered `install.sh`. The archive contains
only the complete tracked `skills/agent-memory/` artifact: no `.git`, development
memory, repository docs/tests, bytecode or private state. Read tracked bytes and
executable modes from one clean exact Git source. Use canonical 0644/0755 modes.

The signed manifest binds schema, repository, immutable tag, semantic version,
full source commit, archive name/size/SHA256 and complete portable artifact digest.
Reject duplicate/unknown fields and invalid identifiers. Bound metadata, archive,
expanded bytes, member count and network duration. Verify the SSH signature before
trusting manifest contents, then archive length/hash before extraction. Permit
only ordinary directories and regular files under the exact portable prefix;
reject traversal, absolute paths, duplicate members, links, special files and
unexpected modes. Recompute artifact identity/version before candidate execution.
Never normalize active or custom source permissions.

Keep the current installed `source/skills/agent-memory/` layout, with verified
release metadata/signature beside it. Introduce explicit source kind `release`;
do not fabricate a Git checkout or signed merge commit. Custom managed-Git and
development sources keep their current policies and operator-selected labels.

## Key and bootstrap boundary

Pin the new AM Ed25519 public key in the bootstrap and portable artifact:
`SHA256:uDX57bD5Tg5OewLWafY0X0LgcbMg45RXQwcm98nharc`.
Use principal `release@agent-memory`, namespace `agent-memory.release`.
The private key remains outside Git in an owner-only directory. The publisher
accepts its path and verifies it matches the pinned key; never print or package
private material. Test keys are isolated fixtures. No unsigned fallback.

The bootstrap contains its verifier and pinned key; never execute a separately
downloaded unverified helper. Generate its verifier from reviewed shared source
rather than maintain two algorithms. The fetched bootstrap itself remains the
initial HTTPS trust anchor. Rotation requires old-key authorization or an explicit
new operator trust decision, never a downloaded replacement key.

## Update and existing installations

Resolve latest stable release, then pin asset reads to that exact tag. Require
agreement between locator and signed manifest. Order signed releases by semantic
version, not Git ancestry: refuse downgrade or replacement of an existing version
by a different artifact. The source commit is provenance. The publisher MUST refuse an existing tag or
release rather than overwrite a previously published version; signed identity
and publisher refusal must not be mislabeled as GitHub-enforced immutability.

Reuse existing ownership/private-path checks, journal, backups, compatibility
observation and locked readback. Activate through that transaction. An unchanged
signed update is quiet and read-only. Preserve bank data and unrelated client
configuration; never migrate memory during update. Rollback uses the exact owned
predecessor and retains #48's bank readability/restoration requirements.

The new updater automatically adopts signed releases for a validated owned
legacy installation of the official default Git repository/main channel. Validate
old source and all old targets under the original receipt, then journal the
source-kind transition and retain its predecessor. Require a newer release version,
or exact same-version portable paths/bytes and Git executable intent. For the
latter legacy case, verify actual modes under the original receipt, but compare
Git executable intent with the canonical signed modes; a legitimate old umask 002
checkout can have 0664/0775. Never chmod old source or call its merge commit signed.
Activate the independently verified canonical archive, not the old checkout.
This limited legacy equivalence does not permit replacing an already-signed
version with a different artifact identity. This does not weaken the
fast-forward policy for installations that remain managed-Git. Custom channels
and development sources never change channels silently.

The already-running v0.0.2 updater cannot retrospectively verify signatures.
Its first activation keeps its HTTPS/fast-forward boundary. Report that activation
as legacy unsigned; a subsequent verified update or a freshly fetched trusted
installer establishes signed activation. Having signed bytes available is not
proof that the executing installer verified them. Wire #173's diagnostics to the
actual recorded trust path, including recovered and rolled-back activations.

Publish and read back the complete signed release before activating either the
public default bootstrap or the release-only updater. Keep that activation on
the reviewed release-integration branch until the first signed release exists;
landing code that the old updater loads is also activation. Current v0.0.2 has
an unsigned manifest and no signature, so its assets are not a valid fallback.
The publisher owns tag/draft sequencing
under actual repository rules. Preserve concurrent main changes, never force refs
or reuse published versions, and retain the current public journey if publication
fails. The [forward ADR](../adr/0015-signed-release-channel.md) records the approved
channel refinement; implementation and acceptance are separate evidence.

## Acceptance

Extend existing real command journeys: install, unchanged reinstall/check, update,
interrupted update/recovery, rollback, uninstall and reinstall, locally on macOS
and Linux using isolated homes and a controlled release server. Prove invalid
signer/namespace, changed manifest/archive, truncation/oversize, unsafe members,
version replacement/downgrade, missing assets and unavailable transport refuse
before candidate execution while preserving the active installation.

Exercise the actual v0.0.2 updater under umasks 022 and 002, including its
installation of the new runtime before signed-channel adoption. Distinguish its
first activation from a
verified one. Cover official legacy adoption, custom-source preservation,
owned-target refusal, bank compatibility and consumer-memory isolation. Bind
proofs to exact candidate/artifact identity. Independent review must compare the
public journey and retained machinery against C2E/AWA before acceptance.
