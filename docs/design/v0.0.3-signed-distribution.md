# v0.0.3: signed immutable distribution (#49)

Status: proposed technical design, pending independent review and the operator's
update-channel and signing-key choices. ADR-0014 brings existing story #49 into
v0.0.3; this document does not grant implementation or acceptance approval.

## Publisher authentication

Use OpenSSH Ed25519 signatures, a dedicated release principal and the namespace
`agent-memory.release`. The release pack and bootstrap pin the public key.
The private half stays outside Git in an owner-only location selected by the
operator. Test keys are isolated fixture material and cannot become the publisher
key. No C2E key is reused. This follows the lifecycle signing pattern inspected
in C2E, without importing its binary packaging or private-repository assumptions.

The trusted verifier checks a detached SSH signature over the exact bounded
manifest bytes before trusting any artifact URL, version, revision or digest.
Reject duplicate JSON keys, unknown schema/fields, nonfinite values, malformed
versions/revisions/digests, unsafe names, oversized inputs and wrong repository,
principal or namespace. A signature authenticates the publisher's bytes; it does
not establish code correctness or make the executing verifier trustworthy.
HTTPS protects transport. First bootstrap trust still rests on the fetched
installer and its pinned key; documentation must state that boundary.

## Immutable transport and existing ownership

Package a Git bundle containing one `refs/heads/main` release candidate and its
complete ancestor history. Sign a manifest binding the release version/tag,
full source revision, bundle name, byte count and SHA256, and the complete
portable artifact digest. This retains the existing managed Git layout,
fast-forward ancestry checks, receipts, wrappers, activation and rollback
machinery. It avoids making a new tar extractor or executable downloaded
verification helper part of the trust boundary.

Download into private staging with bounded size/time, verify signature, then
bundle size/hash before asking Git to inspect or clone it. Verify the bundle's
single declared branch, candidate revision, actual package version and artifact
digest independently. No candidate code executes before validation. Use a
private checkout of the verified bundle and restore the recorded canonical
origin only after verifying its provenance. The publisher and verifier must use
canonical Git checkout modes (0644 ordinary tracked files, 0755 executable files)
inside newly created private staging, with a controlled umask, before comparing
the signed artifact digest. Do not normalize an existing active/custom source,
weaken mode binding or reinterpret its receipt. Test caller umasks 002 and 022,
including a signed digest with incorrect executable/mode evidence. Preserve the existing private
ancestor/ownership checks, compatibility checks and under-lock readback.

Normal update discovery uses the latest non-draft, non-prerelease release's
manifest if the operator selects the signed-release default. A release locator
is only a transport hint, never authority to replace the pinned key. A selected
release must match its signed tag/version and must not downgrade or diverge from
the installed ancestry. Retain old runtime and owned-target backups until the
existing transaction commits. No runtime operation migrates a memory bank.

If the operator retains `main` as the normal locator instead, the same signed
manifest must bind the exact located revision; an unsigned newer branch tip
cannot be activated. This is a distinct channel choice, not a silent fallback.
Explicit custom/development sources retain a clearly labeled operator-selected
trust boundary and never receive a false publisher-authentication claim.

## Upgrade and key rotation

An already-running v0.0.2 updater is unsigned software and cannot retrospectively
gain publisher authentication from the new payload. Its first transition uses
its existing HTTPS/fast-forward integrity contract; subsequent operations use
the new verifier. A legacy receipt missing new authentication metadata remains
explicitly legacy-unsigned. The old process cannot record new trust guarantees;
never infer them from a newly installed verifier or payload digest. A freshly fetched trusted v0.0.3 installer can authenticate its
candidate before activation. Exercise both paths and document the difference.
Do not claim that a digest or successful old-process receipt is a signature.

Do not silently replace a pinned key using a newly downloaded manifest. Rotation
requires an independently reviewed transition authorized by the old key or a
separate explicit operator trust decision. Loss of the private key cannot be
repaired by an unsigned automatic channel change. Receipt/journal evidence must
retain which trust path verified the activated candidate.

Source clones and a managed checkout may physically contain this repository's
development bank. The reusable package and client discovery still expose only
the portable skill; installation must not initialize, bind or recall that bank
as consumer project memory. A signed source archive grants no memory authority.

## Acceptance

Run isolated public install/check/update/recover/uninstall operations locally on
macOS and Linux with fixture keys and a controlled release transport. Cover a
trusted release, mutated manifest, wrong signer/namespace, changed bundle,
wrong revision/version/digest, oversized/truncated response, missing signature,
downgrade, divergent ancestry and unavailable locator. Every rejection preserves
the active runtime, receipts, client configuration and project bank.

Interrupt activation and retry through the existing journal; read back exact
ownership and trust evidence. Keep unchanged-update checks read-only and quiet.
Exercise the actual released v0.0.2 process, the new verified bootstrap, explicit
custom-source qualification and consumer-memory isolation. Bind acceptance to
exact source and portable hashes with independent review. No production key
generation, signed release publication or change of default channel is implied
by fixture qualification or this proposed design.
