## How / ordered execution / method / outputs

1. **Bind intent and assumptions.** Build a requirements-to-section matrix from all four #246 acceptance bullets and ADR-0008. Separate current same-repository behavior from hypothetical federation. Create a numbered assumption ledger with source, confidence, decision owner, validation method and provisional consequence. Initial shared assumptions: project UUID is distinct from repository URL; catalog membership is distinct from read permission and export consent; public repository does not imply export authorization; no private project existence/description/link is discoverable without permission.
2. **Catalog concrete use cases, not an abstract platform.** Analyze at least the following hypothetical cases; label each as operator-confirmed, source-motivated or unvalidated: (a) public SDK and public server compatibility/dependency lookup; (b) private application and private deployment repository ownership/contract lookup; (c) public library plus private consumer, where merely naming the consumer is sensitive; (d) several clones/worktrees of one repository, which must NOT become separate federation projects; (e) fork/rename/host migration, with explicit link/rebind/fork decisions; (f) leaving an ecosystem or losing access while old relations remain. For each record actor, information need/query, source and destination, minimum metadata, who may discover it, deliberate consent, stale/removal behavior, potential harm and whether plain repository documentation already suffices. Do not invent a real relationship or copy actual knowledge across projects.
3. **Collect input without stalling analysis.** Use already available operator statements and record Vince's actual input if supplied through the operator. No Vince input was supplied to this planning assignment: mark **unavailable, not negative evidence and not a research-start blocker**. Continue with explicitly unvalidated use cases and bounded alternatives. Prepare one highest-impact question at a time for the operator; record date, exact answer/source and affected assumptions. Do not infer Vince's preferences from the ADR's mention of him. Operator decides whether unavailable input warrants a conditional recommendation, deferral of a product choice, or later consultation.
4. **Compare identity and membership options.** Reuse ADR-0011's stable UUID and explicit evidence/alias resolution; contrast UUID-backed manifest with remote-only and directory/access-inferred membership, documenting why the latter conflict with source requirements. Cover cloned IDs, same URL/different IDs, different hosts/forks, no remote, rename, multiple remotes, stale authority, copied bank and membership removal. Define proposed manifest fields (stable federation/project IDs, sanitized repository location, approved description, typed links, membership authority/version, visibility/consent reference) as a research sketch, not a shipped schema. Compare repository-owned versus federation-owned explicit membership approval, one-sided enrollment versus mutual enrollment, and admission/removal/renewal responsibilities. Separate who can propose from who can approve and who can read.
5. **Compare public/private visibility and consent.** Produce a matrix for public→public, public→private, private→private and private→public, including private existence, name/description, repository URL, typed relation and exported-content discovery. For each compare deny-by-default/per-entry approval, destination-specific approval and a narrowly scoped standing grant with review/revocation. Local read access, hosting membership and developer ID NEVER constitute transfer permission. Distinguish catalog-only metadata consent from content-export consent; publicizing a private relation requires separate deliberate authority. Compare metadata-minimal pointers versus richer discoverable summaries against each use case and leakage risk; do not silently approve any option.
6. **Evaluate and recommend.** Apply hard filters first: explicit membership and consent, stable identity, no sensitive metadata disclosure, portable independently useful local bank, and no inference of transfer rights. For surviving options score scenario coverage, operator burden, failure/revocation clarity, auditability, implementation/operation complexity and residual leakage qualitatively, with rationale and sensitivity to unavailable Vince/operator input. Recommend the least complex justified boundary (including no catalog if use cases remain unsupported), rejected alternatives, risks, who owns each unresolved decision, and the minimum separately reviewed follow-up design. No numeric benefit claims or assumed graph need.
7. **Join review with #247, then independent review.** Both researchers draft steps 1–6 concurrently. Exchange a versioned assumption table at initial drafting and reconcile identity, authority, metadata visibility, grants, revocation/removal and offline handling. Each final brief cites the shared join ID and the other brief's pre-join revision, not its own final hash. A separate canonical join record in review evidence binds that ID, both final brief blob hashes, agreed assumptions, disagreements and decision owners. Review that record and exact final bytes independently; if either brief changes after review, its earlier verdict no longer applies and the changed bytes and updated join require re-review. This is research integration, not a feature dependency.
8. **Operator disposition and delivery.** Present recommendation and remaining choices one question at a time, and record accept/revise/defer/reject of the recommendation separately from acceptance of the brief as a complete, reviewed research record. An operator's defer or reject of the recommendation remains valid research delivery when the artifact itself is independently reviewed and accepted; neither disposition approves #55 implementation. Land the accepted research record and evidence through normal repository review, then include that exact reviewed record in published v0.0.15. Parent records acceptance/integration/release evidence; a draft or merged document alone is not published delivery.

## Acceptance / independent review / operator disposition

- **AC1:** all concrete use cases have actor/query/sensitivity/authority and input provenance; actual operator/Vince input or explicit unavailability and questions are present.
- **AC2:** stable identity, explicit membership, all public/private directions and consent alternatives are compared; repository access is explicitly not transfer permission; directory/access-inferred membership is not adopted.
- **AC3:** recommendation, credible alternatives, risks, decision owners and follow-up design are explicit; #247 is referenced and joined without waiting for catalog/export features.
- **AC4:** independent source-bound technical verdict and operator disposition are retained; open product choices remain open; feature implementation requires a separate decision. Findings may recommend deferral without pretending research failed.
- Review method: reviewer traces each AC to source and artifact sections; adversarially walks every scenario for identity collision, metadata leakage and consent confusion; checks join consistency and that no proposal is reported as implemented. Blocking review defects require revision/re-review; merely unresolved product preferences require named owner and disposition, not fabricated answers.
