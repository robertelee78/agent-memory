# v0.0.3: explicit recoverable bank migration (#48)

Status: proposed technical design, pending independent review. ADR-0014 preserves
the migration outcome in v0.0.3; implementation approval, acceptance and delivery
remain separate. This design does not introduce a new production bank schema.

## Runtime compatibility and the initial catalog

`agent-memory/v1` remains the only production format. Ship no fictitious v0/v2
format and advertise no migration source until a complete reviewed converter
chain actually ships. The production migrator catalog is initially empty, as
is `migrator_source_schemas`. Current v1 banks remain directly readable.

Provide an explicit `am migrate` interface and recoverable engine that future
reviewed releases can populate. A current-format preview reports no migration
needed and writes nothing. Unsupported formats without a complete bundled chain
refuse before canonical changes, with a bounded explanation. The catalog and
runtime compatibility declaration must agree, including missing intermediate
steps, cycles, ambiguous routes and unreachable destinations. A declaration
alone cannot make an unsupported bank readable or create a converter.

Migration codecs/converters are fixed, reviewed Python shipped in the trusted
portable package. They are not code, paths, commands or policy loaded from a
memory bank, downloaded plugin or caller proposal. The release identifies each
codec/step and its source bytes. A step validates its complete source and target
representations and preserves project identity, record identities, conditions,
evidence, provenance, lifecycle history and tombstones. Format conversion grants
no authority to consolidate claims, broaden applicability or resurrect memory.

## Observe, preview and apply

Use the existing repository/bank locator, ordinary-path/alias checks and one
physical bank lock. Migration must inspect the source header before native-v1
validation, since an older supported source can be unreadable to ordinary recall.
A dedicated migration-only identity path must prove the existing registry,
checkout, canonical repository and source codec's validated project UUID agree.
It cannot create/rebind identity or weaken normal recall/mutation resolution.
Unknown developer/project binding remains an actionable refusal.

`am migrate preview --repo PATH --to SCHEMA` produces a private source-bound plan:
actual bank/project identity, source/target schema, exact converter chain and
code hashes, complete source/result inventories, changed paths and recovery
requirements. The helper must fully validate both representations before
offering apply. Human output remains concise; explicit JSON carries the plan.
Preview does not create canonical files, move memory, activate runtime code or
make a backup that could be mistaken for an applied operation.

The plan must not embed or execute instructions from memory. Source data remains
untrusted. Reads use bounded ordinary single-link files, no-follow ancestors and
portable alias checks; unsupported paths, special files, symlinks, unknown files,
oversized inventories and changed sources refuse without truncation. Size limits
are explicit implementation bounds, not capacity or retrieval-quality claims.

`am migrate apply --proposal PRIVATE_FILE` rechecks the trusted catalog/chain,
resolved identity and complete source inventory before and under the common
bank lock. Before its first canonical edit it writes a complete private backup
outside the bank and managed runtime, verifies every backup byte/hash, and
durably journals the original plan and before/after inventories. Neither the
installer ownership receipt nor runtime update owns or removes this backup.

Use the existing visible `.agent-memory-transaction.md` stop boundary with an
explicit migration marker format. Current and older normal readers must refuse
while it exists; the generic transaction recovery helper must not reinterpret a
migration journal. Migration recovery has its own bounded route. Write each
planned path with existing atomic replacement/no-overwrite principles, preserve
modes where the format permits, detect unexpected edits before each replacement
and read back the complete target through its codec before committing a receipt.
Do not claim one globally atomic multi-file or cross-filesystem switch.

The receipt records the exact operation, project/bank, source/target schemas,
converter/code identities, original/resulting hashes and backup location. It
certifies the observed conversion outcome, not semantic truth, Git publication
or another machine's freshness. The bank remains normal repository Markdown;
publication and turn-boundary refresh are separate operations.

## Recovery and runtime rollback

`am migrate recover` first inventories owned lock, marker, journal, backup and
receipt. It must not steal live/unknown locks, infer ownership from age or delete
unrecognized state. Recovery preview lists the exact finish/rollback delta.
Finishing uses the recorded plan and original converter/code pins rather than
recomputing a different interpretation from today's sources. Changed converters,
external edits, missing/corrupt backups or unknown partial states require
inspection. A verified completed receipt permits cleanup/readback, never replay
over later corrections.

Rollback restores the exact verified before bytes from the private backup,
preserving later unrelated edits by refusing an unexpected participant or path.
The implementation must state whether the current helper can revalidate that
source codec or only prove mechanical exact-byte restoration. Lack of a current
codec cannot silently become a claim of readable source format. Recovery from a
release that removed the required codec may require its trusted retained package;
documentation must give that bounded route before any migration is offered.

Runtime install/update never calls migration. Before activating an ordinary
candidate, including exact pre-transaction runtime rollback, compatibility checks
must establish that discovered banks are directly readable or have the declared
complete supported migration path. A post-migration rollback to a runtime that
cannot read the current bank must stop until explicit reverse migration or
verified original-backup restoration makes it readable. An undiscovered or
offline bank remains a discovery gap, not proof of compatibility; encountering
it later still refuses unsupported normal mutation. Runtime rollback must not
silently restore project memory or remove migration evidence.

## Acceptance and limits

1. Through installed public commands prove native v1 no-change, unsupported-source
   refusal, complete/incomplete catalog declaration checks and unchanged banks
   across runtime check/update. Production continues to advertise no converters.
2. Exercise the same engine/public CLI in an isolated fixture release containing
   explicitly labeled test-only schemas/codecs and a multi-step converter chain.
   Fixture schemas never ship in the production catalog and are not represented
   as real historical Agent Memory formats. Validate full identity, preservation,
   backup, readback and truthful receipts, rather than mocking internal writes.
3. Interrupt before/after backup, marker, individual replacements and receipt;
   test finish, original rollback, lost-response replay and refusal after newer
   external edits or corrupt/missing journal/backup. Ordinary recall stays stopped
   during a partial migration, and developer/project identity cannot change.
4. Exercise runtime downgrade/rollback with both readable and migrated-unreadable
   fixture banks. Require explicit restoration before incompatible activation;
   prove memory, client content and owned runtime survive refusal/recovery.
5. Qualify the changed boundaries locally on macOS/Linux using isolated homes,
   worktrees and banks, exact source/artifact hashes and independent acceptance.
   Retain actual failure evidence. No expensive hosted matrix, personal memory,
   implicit bank upgrade, new storage service or production schema transition.

This release provides migration mechanics and verified refusal with an empty
production converter catalog. A future real format transition still requires
its own reviewed source/target codecs, complete chain, preservation evidence and
supported rollback route before its source schema can be advertised.
