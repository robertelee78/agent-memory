# v0.0.3: selective initialization routes (#167)

Product outcome: ADR-0014's accepted distinct-initialization-routes section.
Technical approval and implementation acceptance remain separate.

## Design

The six ordinary context roles already have distinct meanings in ADR-0010.
Initialization will use one small canonical route-profile function for each
new context, shared by proposal generation and transaction revalidation:

| Context | Purpose | Selective read trigger |
| --- | --- | --- |
| projectbrief | Project purpose and authority boundaries | At session start to identify the project |
| productContext | Users, workflow and scope exclusions | When deciding product scope or comparing requirements |
| activeContext | Scoped handoff, unresolved questions and next step | When resuming the matching task or investigating its questions |
| systemPatterns | Architecture and established project patterns | When changing design, integration or project conventions |
| techContext | Qualified implementation and technical source evidence | When working on the relevant implementation or tooling |
| progress | Delivery evidence and work-source references | When checking delivery claims or release scope |

These role defaults describe navigation, not universal statement applicability.
They must not silently replace an existing useful custom route, loosen scope,
promote untyped prose to admitted guidance, or treat a handoff as an assignment.

Keep the current input schema and public CLI stable. Use the profile only when
initialization actually creates a previously absent useful context. Existing
contexts/routes remain byte-identical, including purpose/read trigger, scope,
lifecycle and independently qualified conditions. Missing-context checkpoint
preparation uses the same activeContext profile instead of a generic startup
trigger. Ordinary checkpoint updates do not rewrite a router.

Do not add an LLM router, embedding service, new bank schema, empty placeholder
files, inference of task identity, or a second writable registry of memory roles.

## Public acceptance

1. Initialize useful distinct contexts through the installed CLI from reviewed
   documentation/code/ADR/AWA evidence. Read the actual router and assert distinct
   useful purposes/triggers for every created context, with no generic repeated
   startup wording. Empty/irrelevant contexts remain explicitly omitted.
2. Preserve a bank with a custom useful route; initialize another missing context
   and verify the existing files, route scope and trigger are unchanged.
3. Prepare missing active context through the public checkpoint route and verify
   the selective matching-task trigger; an ordinary checkpoint changes no router.
4. Exercise the agent-facing outcome using the actual map: product-scope work
   selects productContext, implementation inspection selects techContext, and
   delivery verification selects progress. The selected context is bounded and
   retains source links and orientation-only qualification. This checks usable
   routing metadata; it does not claim a new automatic query router exists.
5. Run focused initialization/checkpoint/installed-operation regressions locally
   on macOS and Linux. Reuse unchanged schema/transaction evidence; run the source
   validators against the exact candidate and retain output/exit codes.
