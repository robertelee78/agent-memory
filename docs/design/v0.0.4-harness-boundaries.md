# v0.0.4 turn-boundary invocation design (proposal)

Issue: #19. Product intent is one repository-bound Markdown bank, with eligible learning captured and landed and newly landed memory refreshed across independent worktrees and machines. Hooks invoke the existing skill/CLI; they cannot themselves decide meaning, bypass governed admission or imply publication.

## Events and workflow

- For Claude Code and Codex, use their documented `UserPromptSubmit` hook to request the shared memory skill's refresh before task work, and their `Stop` hook to schedule one agent continuation at the end of a substantive turn. The continuation assesses durable learning, invokes the skill's semantic discovery, comparison, admission and publication workflow, and records a verifiable completed, no-learning, conflict or pending outcome. `stop_hook_active`, session/turn identity and private state prevent recursive continuation. A failed or interrupted operation remains visibly pending and does not falsely claim success. No prompt or unrelated tool call is blocked.
- For OpenCode, support the installed versions' actual public plugin and session APIs. The operator's machine has OpenCode 1.19.3 on `PATH` and OpenCode 2.1.3 as `opencode2`; its existing global configuration uses the v2 API and is rejected by v1. V1 documents `session.idle`; V2 uses its session/event domains. Verify event payload, API behavior, turn identity, and error semantics with each actual harness before selecting a mechanism. An idle event without a reliable way to schedule exactly one continuation is insufficient. The plugin must ignore its own continuation events and retain pending state when delivery or invocation fails. Never send a message to another developer.
- The continuation includes a clear instruction for the currently running agent to use the portable skill, not a fabricated learning judgment. Neither a deterministic string match nor a reminder with no observed agent execution counts as capture. A no-learning decision, conflict and inability to publish are explicit outcomes; a passive CLI process cannot know the user's conversation by itself.
- Automatic turn invocation and the distinct semantic/capture/publication workflow are both required. Avoid copying transcripts or credentials to shared memory. Scope is the observed repository; uninitialized or unsupported repositories remain untouched. At the next natural boundary, conflict/failure is surfaced without blocking unrelated work.

## Installation and ownership

Preserve existing client configuration and hooks. Install idempotently through the existing lifecycle receipt and journal; update/uninstall remove only owned artifacts and must retain user changes. Codex non-managed hooks require explicit client trust of exact definitions; detect/report untrusted or unavailable hooks truthfully instead of claiming active. Existing Codex, Claude and OpenCode sessions may need restart. The portable skill/CLI must continue to work without any supported harness or hooks. No daemon, MCP, mandatory external service or personal memory.

## Acceptance

For each of Claude, Codex and OpenCode, on both supported platforms where the harness runs, exercise its actual public runtime event surface in an isolated fixture, omitting explicit skill invocation. Show a durable lesson becomes a qualified shared memory and becomes visible from another worktree; also verify no-learning, duplicate, contradiction, offline/pending, uninitialized project and broken-hook handling. Demonstrate invocation is once per natural turn, does not loop, does not discard feature code and does not publish unrelated content. Repeat install, update and uninstall with preexisting foreign hooks. Validate trust status and missing-harness paths honestly. Fixture models/judgments must be identified; distinguish adapter event delivery from proof of semantic capture and real model behavior. Every individual test must reasonably finish within 10–15 minutes.

## Remaining technical risks

Upstream OpenCode has an open [pre-stop hook request](https://github.com/anomalyco/opencode/issues/16626) describing why `session.idle` cannot reliably continue a one-shot turn before teardown. A tool-after callback is not an equivalent: an agent may finish without invoking any tool, and tool calls are not turn-completion events. `session.updated` reports session metadata, not a synchronous pre-stop gate. These observations support the local race findings; they do not prove all future OpenCode versions lack a usable mechanism.

OpenCode 2.1.3 also supports a synchronous pre-response `ctx.session.hook('context')` model-request transformation. In an isolated GLM-5.3 one-shot run this supplied an instruction to attempt a fixture write without a separate worker. When the project explicitly required approval for edits, the actual `write` tool call was rejected with `executed: false` and no file was created. With edit explicitly allowed, the same instruction led to a successful write and exact expected bytes. This establishes event delivery and permission behavior for those fixtures, not automatic memory capture: the model still interprets and can ignore the injected instruction, and no source-bound capture or publication outcome was checked. Test that separately before claiming success. A context hook within the current turn avoids concurrent mutation of the session and a post-exit worker, but cannot by itself guarantee a completion acknowledgment after the agent's final answer.

A subsequent isolated OpenCode 2 / GLM-5.3 trial used a bound disposable bank, the installed skill and CLI, and a context hook requesting governed admission of a confirmed user decision without an explicit user skill invocation. The trial reached its 180-second timeout with no completed result. Its initial runner did not retain partial stdout on timeout, so the cause and any attempted actions are unknown; it provides no evidence that admission succeeded or failed. Any retry must retain partial results, bank state and the exact reason for stopping.

The corrected 120-second retry retained 40 emitted items and no changed bank files. The model followed the injected request, read the skill and several guides, verified the disposable identity and reported remote freshness pending, but was still examining admission implementation when stopped; no candidate, admission or publication receipt was produced. This is evidence of a practical capture-workflow complexity problem beyond hook delivery. It is not a completed semantic acceptance or a reason to bypass comparison, evidence, privacy or publication gates. The fixture had no shared remote and cannot establish sharing. Source-bound progress records and partial logs must be kept for diagnosis; the test's operator-confirmed fixture statement was not admitted.

A separate bounded OpenCode 2.1.3 / GLM-5.3 run using the shorter turn guide and draft builder completed in 180.9 seconds including fixture setup. The injected context requested capture without a user skill command; the model ran draft, capture, discovery, comparison, preview and apply, receiving `verified: true` and `admission_verified: true` for a production-scoped retry decision. It preserved unrelated staged code and reported its discrepancy with the decision. Independent fixture readback found the router, one topic and one history event changed. This proves one governed **local** admission under that test setup; the disposable repository had no remote and the test prohibited publishing, so it does not prove shared refresh, publication, reliable invocation or behavior in other harnesses. It also demonstrates that this workflow can consume roughly three minutes even with the shorter route.

A concurrent same-session probe ran an independently resumed user request as the detached continuation began. Both clients exited successfully, but the continuation's output stream contained both its own answer and the other request's answer. A client stream or zero exit therefore does not bind completion to one request. Do not deploy detached workers without a mechanism that serializes or rejects concurrent session work and a source-bound completion receipt that identifies the actual operation; a simple process or stream check is insufficient.

An OpenCode 2.1.3 live local probe with GLM-5.3 observed `session.execution.succeeded` and accepted `ctx.session.prompt({sessionID, text: '...'})`. However, `opencode2 run --standalone` exited after the first answer while the scheduled continuation had only started; it did not establish a completed continuation. A separate probe against an owned persistent server recorded two successful executions in one session and the continuation's requested text. An object-valued `text` was refused by the API. A subsequent one-shot probe spawned a detached `opencode2 run --standalone --session ID` continuation; the child finished after the parent exited and correctly recalled a word from the original session. This proves context continuity for that fixture, but not safe operation when a user resumes concurrently, permissions, reliable receipts, recovery or actual learning. A short-lived worker is a candidate, not a required persistent daemon. Technical review requires proving no overlap with a subsequent interactive turn, no unowned permissions or approval bypass, durable crash/pending handling, no duplicate or recursive execution, no hidden cross-session effects and no service dependency before integrating this approach; prefer a synchronous pre-exit hook if supported. These probes establish event delivery, not memory capture or general race safety. Do not use a post-response callback or a successful process start as proof of one-shot capture. Exact OpenCode v1/v2 behavior, Codex trust management, and a durable, source-bound completion marker for each session/turn require further prototypes; no adapter shall be claimed supported until real behavior is demonstrated. Capture of evidence only available during a turn and publication under repository policies must be explicitly tested. Harness requests may be unavailable while the user is offline or has interrupted the session; preserve pending work rather than invent success.
