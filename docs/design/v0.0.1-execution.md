# v0.0.1 execution contract

The operator approved this design for v0.0.1 on 2026-10-22, acting as product
owner and technical reviewer. The [approval record](v0.0.1-approval.md) names
the immutable reviewed revision and all 52 approved work keys. Implementation
and release acceptance require separate evidence.

## Product outcome and boundary

A repository has one shared, readable memory bank. A lesson learned in one
session can become useful to another harness, worktree, computer, or developer
after it lands on `main`. Capture, recall, deduplication, correction, pruning,
and memory-only Git exchange are one first-release experience. The skill owns
semantic judgment; deterministic helpers own validation and verified writes.

The 52 existing v0.0.1 stories remain the scope. Their stable identities,
acceptance criteria, predecessor keys, and source bindings are preserved in
[the execution queue](v0.0.1-work.json). This contract specifies execution and
delivery; the linked ADRs remain the requirements authority. Personal memory,
MCP, cross-repository exchange, signed distribution, and runtime hooks are
outside this release. Hooks remain v0.0.3; explicit skill-guided boundary
invocation MUST work in v0.0.1. Automatic capture means the active skill performs
the learning loop without a separate user request, not that a forgotten skill
invocation is guaranteed to run before hooks exist.

## Delivery and execution order

All stories retain milestone v0.0.1. The 51 implementation and verification
stories deliver on reviewed, accepted merge to `main`; the final release gate
[#96](https://github.com/robertelee78/agent-memory/issues/96) delivers only with
the published, non-draft, non-prerelease v0.0.1 release. A merge alone is not
acceptance evidence. Each story still needs its own candidate, independent
acceptance verdict, and integration proof under AWA before Done.

This removes the former same-release dependency deadlock: a prerequisite can
become Done before the release that contains its dependent. No dependency is
removed merely to advance the board. The final gate additionally depends on
every other v0.0.1 story directly or transitively, so lifecycle, packaging, security, and file usability
cannot be omitted by passing only the sharing scenario.

GitHub supports [at most 50 dependencies per relationship](https://github.blog/changelog/2025-08-21-dependencies-on-issues/).
The gate has 50 direct predecessors; #71 is covered through its dependent
stories. The planning check verifies that the complete predecessor closure
contains all 51 other first-release stories.

The queue assigns a topological wave, with wave 0 containing prerequisites that
can start after approval. A wave is a planning view; the exact predecessor keys
remain the execution rule. Each coding session uses its own worktree and branch.
After prerequisites reach Done, use AWA to select the next Ready story, record
the attempt, and carry that exact story through review. No runtime implementation
or passing acceptance result is claimed by this preparation.

## Implementation interfaces

The approved baseline is Python 3.11+ with an executable `agent-memory` wrapper,
one distributable `skills/agent-memory/` artifact, and a standard-library test
runner. The artifact includes its scripts and schemas; no separately installed
Python package, database, hosted model, or service is a runtime prerequisite.
Code lives inside the portable artifact; repository scripts invoke that same
code. Preserve the existing lifecycle blueprint's ownership and recovery model.

| Boundary | Responsibility | Public acceptance surface |
| --- | --- | --- |
| `identity` | Stable developer attribution, project/bank ID, canonical remote, explicit bind repair | `status`, `project bind` preview/apply |
| `bank` | Router, typed records, validation, current/historical selection, content-free tombstones | `init`, `doctor`, `get`, `checkpoint` |
| `writes` | Lock, observed hashes, atomic single-file replacement, recoverable multi-file journal | All mediated mutations; fault/recovery fixtures |
| `retrieval` | Filter scope/status/validity before lexical ranking, bounded assembly and explanations | `search`, `context`, `explain` |
| `learning` | Candidate admission, search-before-write evidence, consolidation, correction and forgetting | `capture`, `compact`, `correct`, `supersede`, `revoke`, `forget` |
| `sharing` | Memory-only publication/refresh, reconciliation inputs, pending state and retry | `publish`, `refresh`, shared `boundary` operation |
| `lifecycle` | Install/update/uninstall ownership, adapters, rollback and diagnostics | Commands and file paths in ADR-0007 and its blueprint |
| `skill` | Progressive guidance, source authority, semantic decisions and focused clarification | Installed root and reachable guide tree |

These names are internal seams, not independent services or banks. Small
related modules MAY share a file. Semantic capture and reconciliation run in
the invoking agent; the CLI does not silently call a particular model.

Mutations follow preview → reviewed proposal → apply → readback. Previews bind
project identity, candidate IDs, observed file hashes, relevant evidence and
operation identity; apply rejects drift. Read-only commands never acquire a
write lock or silently repair data. Machine output uses `--json` and records
schema version, operation ID, resolved identity, observed/resulting hashes,
changed memory paths, pending/conflict state, and verification result. Successful
durable mutations cannot claim `verified: true` until readback succeeds. Tests
MUST distinguish a committed write with lost response from a write that failed.

The initial schema is `agent-memory/v1`. The reader supports a documented,
restricted YAML frontmatter grammar: top-level known keys; scalar strings,
booleans, nulls, numbers; JSON-compatible flow lists/maps; and block lists of
scalar strings. Reject duplicate keys, aliases/tags, unsupported nesting and
malformed metadata rather than interpreting it differently across clients.
Canonical writers use that grammar; human-readable Markdown bodies are
unrestricted. #7/#26/#71 publish exact field schemas, round-trip fixtures and
errors before consumers merge. Extending the grammar requires a shared reader
change, never a client-specific parser.

Router and record fields follow ADR-0010. Applicability includes repository,
component, branch/worktree/task conditions where relevant; developer, harness,
session, evidence, validity and lifecycle state remain distinct. The six context
files MAY contain concise prose without per-paragraph records. Transient
observations, locks, journals, retries and caches are excluded from publication.
Tombstones contain IDs, lifecycle facts and safe references, never deleted prose.

## The boundary learning loop

1. Resolve the repository and developer; read the router and applicable existing
   memory. Inspect initialization evidence from docs, code/tests, ADRs and AWA
   when needed. Keep approved intent, observed behavior and planned work distinct.
2. Fetch and detect landed memory on the authority branch, then prepare the
   memory-only three-way refresh. Reconcile incoming corrections and tombstones
   before relying on affected guidance. Preserve unpublished local learning.
3. Identify useful durable learning from the completed turn. Search existing
   plausible matches, read their contents and evidence, and classify each
   candidate as duplicate, compatible refinement, conditional distinction,
   contradiction, obsolete guidance or genuinely new learning.
4. Apply small evidenced changes. Combine duplicates, tighten wording and prune
   obsolete content while preserving distinct conditions, sources and provenance.
   Do not prune merely because a lesson is old or an older branch still uses it.
5. Publish only eligible memory changes through existing repository rules,
   rechecking matches against the latest main before landing. Record pending
   state when offline, review is required, or reconciliation cannot finish.

The CLI requires a proposal tied to the searched/read versions and presents
plausible matches; it cannot prove semantic completeness. The skill MUST perform
that judgment, including clean textual merges with contradictory meanings.
Routine successful work stays quiet. Surface conflicts, failures and consequential
corrections promptly at a boundary. If the session never invokes the skill,
v0.0.1 does not claim hook-level enforcement.

## Memory-only Git exchange algorithm

`main` is the initial authority branch; an explicitly configured equivalent MAY
be used. Resolve its remote without changing the operator's global credentials.
Fetch into a tracking ref. Use an isolated temporary worktree/branch based on
the observed authority head for publication; never merge a feature branch to
publish its memory. The candidate commit's ancestry and changed-path diff MUST
prove it contains no unpublished feature/code commits or non-memory changes.
Reject symlinks, paths escaping the bank, runtime files and secrets before staging.

Compute the memory delta against the session's last reconciled authority bank.
Prepare a three-way result from that base, the current local bank, and the latest
authority bank. A missing base/cursor requires reconstructing it from Git or an
explicit reconciliation; it never licenses replacing local files wholesale.
Run the semantic proposal against latest authority content, including records
with different paths but overlapping concepts and applicability. Observed-head
changes invalidate the proposal and trigger bounded retry and fresh review.

Use the repository's existing PR/check/review policy. Direct fast-forward
publication is allowed only where existing rules allow it. A successful push
is not proof of landing on main; read the authority branch and verify the
intended delta or its reconciled equivalent. Required human review remains
pending. No force push, protection changes or silent approval. Recheck current
remote state after lost responses before creating another commit or PR.

A last-moment fetch is not an atomic base-head guard for a hosted PR merge.
Automatic landing requires a server-enforced freshness condition, such as the
repository's existing up-to-date-branch or merge-queue checks, bound to the
reviewed proposal. If the available merge path cannot preserve that condition,
leave publication pending and explain the missing guard. Never change branch
protection or claim that a PR-head check alone guards its base branch. An
advanced-base race belongs in the public sharing acceptance fixtures.

Refresh applies the three-way bank result through the observed-write transaction
helper to the session's memory files only. It does not merge/rebase the feature
branch, change its HEAD, or stage/unstage unrelated files. If memory itself has
staged changes, refresh reports a bounded conflict instead of rewriting their
index representation. Before applying, verify HEAD, index and non-memory files
still match the observed state; after apply verify that they remain unchanged.
Persist the new base/cursor only after successful bank readback. A failed fetch
leaves local memory usable and reports stale/pending sharing.

Refresh bases and applied cursors are disposable state for the specific
checkout/worktree and branch context, not a single repository-wide mutable
cursor shared by concurrent sessions. Keep the fetched/observed head distinct
from the successfully applied authority-bank version. The next three-way base
is the authority bank that was incorporated, not the merged local result that
also contains unpublished learning. Record resulting local hashes separately.
Do not advance an applied cursor after a conflict, interrupted write or failed
readback. Missing or incompatible base state requires reconstruction or explicit
reconciliation; it never permits overwriting local memory.

Git alone cannot merge meaning. Same-wall yellow versus blue with matching
conditions requires clarification even if both records append cleanly. Ask the
detecting developer/session; show other-developer provenance and recommend
clarification with that developer when needed, without sending a message on the
user's behalf. Freeze disputed memory and dependent actions; independent
learning MAY continue. Different branch conditions can justify retaining both.
Deletion and later ordinary code merges MUST honor tombstones and reconcile
already imported learning, without resurrection or duplication.

## Acceptance and release proof

The implementation adds `scripts/test.sh` as the single offline gate in #59.
It invokes real public commands in isolated temporary home/XDG/client/state
roots, local repositories and a bare remote. It returns nonzero for a failing
contract. The test runner MUST refuse live-home paths and clear inherited
credentials/network dependencies. The planning check available now is
`python3 scripts/check_execution_plan.py`; it does not test runtime behavior.

| Contract fixture | Required observable result |
| --- | --- |
| `bank-roundtrip` | Minimal useful bank, bounded router, typed records and safe metadata errors; deleting generated state leaves readable truth |
| `identity-isolation` | Same repo across worktrees/clones and adopted developer ID across machines; explicit fork/ambiguous-remote handling |
| `observed-writes` | Hash mismatch refuses; concurrent processes cannot overwrite; interrupted and lost-response writes converge |
| `learning-admission` | Existing matches read before write; duplicate/conditional/new/unsafe candidates handled with evidence retained |
| `retrieval-context` | Current applicable memory found; historical/revoked/irrelevant content filtered; bounded results expose reasons and sources |
| `correction-erasure` | Correction, supersession, revocation, omission and deletion stay distinct; tombstones do not retain deleted prose |
| `initialize-evidence` | Preserve existing bank; distinguish approved ADR intent, code behavior and AWA planned work; focused Q&A for true conflict |
| `cross-clone-sharing` | Unfinished code in A publishes memory; B with another harness/developer recalls it after refresh; feature ancestry, unrelated working files and index unchanged |
| `concurrent-sharing` | Compatible edits and duplicate lessons reconcile; same-wall contradiction prompts detecting developer; distinct conditions remain |
| `offline-replay` | Offline capture works; interrupted push/merge and lost responses converge without duplicate publication; freshness is honest |
| `later-code-merge` | Normal later merge/rebase preserves already imported learning and honors pruning/tombstones |
| `portable-lifecycle` | Install, reinstall, update/check, rollback, uninstall and explicit purge obey ownership, preserve data/config and work with spaces/copy/link modes |
| `security-canaries` | Untrusted memory cannot grant authority; injection/secret/scope/deletion canaries pass through public operations |
| `skill-routes` | Runtime-loaded leaves remain reachable, bounded and semantically complete; command examples are observed output |
