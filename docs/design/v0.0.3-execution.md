# v0.0.3 execution design

The operator selected v0.0.3 execution after reviewing its eleven open outcomes.
This document records technical designs as they are reviewed. Product scope,
technical design review, implementation acceptance and release publication are
separate facts. A story becomes Ready only with independent approval of its
specific design below; this document grants itself no approval.

## Order and boundaries

1. #172 establishes lifecycle trust-path checks before the signed channel #49
   activates runtime code. Existing transaction/ownership behavior is retained.
2. #167/#168/#169 repair routing, source applicability and scoped handoff;
   #170/#171/#173 establish actionable diagnostics, safe inspection and an honest
   security contract. Independently valuable changes keep separate attempts.
3. #48 defines explicit recoverable migration separately from runtime update.
4. #98 and #99 qualify actual recall and reliability, including the previously
   agreed workloads. Test counts or successful storage do not establish quality.
   Baseline measurements precede any reviewed numerical performance tolerance.

All work uses separate topic worktrees and source-bound AWA records. Heavy
qualification runs on the operator's local macOS/Linux machines. Source clones
may contain development memory; install/update must never inherit it as another
project's memory. No personal memory, MCP, cross-project transfer or v0.0.4 hooks
enter this release.

## #172 — Lifecycle trust paths

Threat: another untrusted local OS principal can write or replace runtime code,
ownership/recovery records, locks or their containing entries. The running user,
root, the selected source publisher and an already compromised process are outside
this particular local-path protection. Signature verification is separate #49.
These checks require a trusted executing verifier. Python has already loaded an
installed helper before its in-package checks run; a runtime previously writable
by an attacker cannot authenticate itself. Inspection/recovery of that runtime
must use a trusted outside helper. This story does not redesign the launcher or
claim pre-import authentication of the executing installation.

- Introduce a standard-library trust-path validator shared by installation,
  update, uninstall, recovery and doctor. Run it before reading installation
  records, selecting executable candidates, or enabling lifecycle writes, and
  recheck under the existing lifecycle lock before activation/removal/recovery.
- External installation-state directories must be ordinary, current-user-owned
  and private (no group/other permissions). Receipt, journal and lock records
  must be current-user-owned ordinary single-link files, not group/other writable.
  Missing paths are checked through their existing ancestors without creating
  them. Malformed/untrusted records remain untouched.
- Ancestors must be owned by the current user or root. Walk from root toward the
  target so a later private directory cannot excuse replacement of its own entry
  through an earlier writable non-sticky parent. An already-established private
  ancestor may protect later group-write payload files/directories from traversal.
  A root-owned sticky temporary parent is exempt only when its direct protected
  entry belongs to the current user/root; a foreign substituted entry refuses.
  Preserve native macOS canonical temporary paths.
- Executable payload/target trust checks retain the final symlink node instead
  of following an unrelated collision. Follow only an already-proven owned client
  link to its separately verified runtime. Sensitive hardlinked records refuse.
  Owned runtime files must not be writable by an untrusted principal: an ordinary
  private ancestor may provide traversal protection for inherited group-write
  payload modes, but cannot excuse a replaceable non-sticky ancestor entry or
  non-private installation-state leaf.
- Newly created installer-owned state remains 0700 and records 0600. Do not chmod
  existing user directories or files. Refusal explains the exact path and offers
  owner repair or a private per-user XDG/client target. Intentionally shared,
  writable runtime layouts have no implicit trusted-group allowance in v0.0.3;
  root-owned read-only managed parents remain supported. Repository memory-bank
  sharing permissions are unchanged.
- Doctor distinguishes access/readability from trust, reports the same policy
  failures without probes, and does not imply that a Unix-mode check audits all
  platform ACLs or protects against the executing user's own malicious process.

Acceptance uses actual public CLI commands with isolated homes: private default
install/update/uninstall/recover; pre-existing 0777 state refusal before writes;
non-sticky writable ancestor refusal; root-owned sticky temporary-root success;
foreign ownership where available; ancestor-substitution refusal and multi-link
owner/receipt/journal/lock refusal; symlink records refused and tampered targets
preserved; v0.0.2 upgrade under ordinary and group-writable umasks where
private traversal makes the installed payload safe. Hash snapshots prove refusal
preserves targets/records and the repository bank. Run on macOS and Linux and
reuse existing transaction fault proofs unless a changed write boundary requires
additional focused interruption coverage.

## Remaining technical designs

#49's production release key custody is awaiting the operator's answer. A new
test key is never substituted for a publisher key. Verification and adversarial
fixtures can be developed with isolated test keys while production trust remains
pending. The other stories retain their source acceptance criteria until their
concrete technical sections receive independent review.
