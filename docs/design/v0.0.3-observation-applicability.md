# v0.0.3: observation evidence versus applicability (#168)

Product authority: ADR-0014's accepted observation-evidence-and-applicability
outcome. This design requires independent technical approval.

## Design

Keep one repository bank and the current native schema. Initialization's source
inventory already records exact SHA256 bytes and the observed branch/HEAD.
Render those facts as observation provenance for new reviewed implementation
claims, separately from the claim's existing `scope` and `conditions`:

- Each local source reference retains its inspected SHA256 and byte count.
- Record observed branch/HEAD as checkout context, explicitly not proof that
  those bytes were committed, published or universally applicable.
- A working-tree content hash binds the inspected bytes even when they are not
  committed. Do not manufacture a commit permalink to uncommitted bytes or infer
  publication from the branch name `main`.
- Git context still pins a pending write proposal and may make that proposal
  stale. A stale proposal is separate from the validity of stored learning.

Preserve the existing conservative branch/revision requirement for old claim
inputs. Add one optional bounded `applicability_review` string to a reviewed
implementation claim. When a session explicitly explains why the inspected
behavior applies independently of its capture checkout, it may use the actual
semantic conditions without adding an artificial branch/HEAD restriction merely
to pass initialization. The existing current/applicable/qualified review flags,
source-domain checks, same-project evidence, explicit condition grammar and
unknown-condition exclusion still apply. A reason string is an agent assessment,
not proof of correctness or permission to broaden a stored claim.

If branch/revision scope or conditions are supplied, continue checking them
against the observed checkout. Genuine branch/task/environment dependencies
remain conditions even when a reason is supplied. Do not automatically strip
conditions from existing memory, migrate stored prose, infer applicability from
Git ancestry, or equate unchanged bytes with universal validity. A session must
inspect semantics and compare existing memory before choosing conditions.

New provenance lines must not manufacture duplicate learning on a subsequent
initialization pass. Match the existing reviewed fact, fact_key, value, summary,
evidence references and semantic conditions independently of the observation footer.
Already represented orientation stays in its original context; changed evidence
requires inspection, not duplication into another missing file. If that same
fact's recorded local-source hashes differ from inspected bytes, return a visible
evidence-review gap; do not call it equivalent current source proof. A legacy
claim without a provenance footer has unknown historical byte binding, also
requiring explicit qualification. These gaps do not invent a new fact or rewrite
the existing file. Initialization
continues preserving existing files byte for byte. Correcting an existing claim
or its conditions uses the existing governed correction workflow, with its
evidence/history preservation rules: untyped orientation uses independently
reviewed observed-file/multi-file replacement, preserving conditions and evidence;
typed records use their existing record-governance operations. The typed govern
CLI is not a prose-target writer.

The full initial/source inventory and exact source/HEAD revalidation remain part
of the private transaction proof. Rendering the footer must use that observed
inventory, never caller-supplied invented hashes. Recovery revalidates its
original source pins. Readback still labels ordinary context `orientation-only`,
with unverified assertions and no typed trust. No new automatic evidence
watcher, query engine, or source-policy authority is introduced.

## Acceptance

1. Through an installed CLI, initialize a reviewed implementation claim whose
   semantics are independent of capture branch, explicitly explaining that
   judgment. Verify source hashes/provenance are separate from applicability.
   Commit only memory, then recall the unchanged referenced behavior: a changed
   memory-only HEAD does not create a synthetic applicability failure.
2. Change the inspected implementation after preview: apply must refuse the
   stale source proof without changing the bank. Read stored old provenance as
   a qualified historical observation, not certification of changed code.
3. Retain a genuinely branch-dependent claim and verify explicit conditions and
   orientation-only reader qualification survive a different branch. This story
   does not claim machine filtering of statement conditions inside ordinary
   prose; prose-aware recall/assembly enforcement belongs to #169. Existing typed
   record conditions keep their actual gates. Preserve legacy inputs and checks;
   missing explicit semantic review still refuses branch-free implementation
   claims. Unknown conditions stay unresolved.
4. Repeated initialization must not duplicate a fact merely because the new
   renderer adds provenance or the capture HEAD changed. Existing context bytes,
   conditions, evidence and attribution remain preserved.
5. Qualify the focused installed/source tests locally on macOS/Linux, bind exact
   source/artifact identities, and independently review the actual outcomes.
