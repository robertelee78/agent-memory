# v0.0.15 Rust-only cutover

Status: operator-directed language change (ADR-0029). Detailed design independently reviewed three times by Claude Opus 5.5 (12 findings, then 9 closed + 6 new, then document-level corrections which are applied here). Implementation status is tracked on the issues, not in this file.

Baseline: `78eaf70a3cfc7c7e3c9444435715d7d437c242dd` — 560 tracked Python files / 110,274 lines (skills 147 / 38,314; scripts 57 / 5,334; tests 273 / 48,813; docs 80 / 16,979; data 3 / 834); 96 runtime modules / 36,739 lines. Measured inputs: [`import-graph.json`, `tier-assignment.json`, `json-codec-call-sites.json`](../research/data/2026-11-13-rust-cutover/).

## Why

The operator requires a native Rust implementation without an interpreter dependency. Language migration must preserve durable memory and governed safety properties rather than reducing the product to a smaller CLI that merely builds. Rust alone does not establish filesystem-race safety, native source authority, retrieval quality or lifecycle correctness.

## What stays authoritative

The existing Markdown bank and public command outcomes remain the compatibility baseline. Rust must directly read existing `agent-memory/v1` banks without rewriting them. Developer/project identities, evidence and provenance, unknown-section preservation, quarantine/secret controls, bounded router navigation, observed-write conflicts, recovery journals, explicit review/admission boundaries, sharing and source-bound receipts must retain their meaning. Existing signed release receipt formats require an explicit compatible transition, not silent adoption of unverified ownership.

Public command names and documented arguments remain, unless a change is explicitly approved and migrated across every caller. Legacy `.py` file paths are not preserved as executable aliases. Current documentation and all Codex, Claude, OpenCode and OMP invocations must use the Rust executable. The OMP TypeScript adapter remains a necessary native-harness adapter; it must call Rust directly, never Python.

## Decisions

| Topic | Decision |
|---|---|
| Targets | `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl` (static). Other hosts refuse in the bootstrap with a named-target message. |
| Qualification platforms | Tests and qualification run on the three release targets only (CI runs the whole suite natively on each). GNU Linux builds are developer conveniences: release-fixture tests may fail there, and that is not a release defect. |
| Existing Python installs | No Python bridge release. v0.0.14 and older require a one-time reinstall via the new bootstrap, which adopts Python-era state (below). From v0.0.15 on, `am update` works Rust-to-Rust from signed releases. |
| Rollback | Journaled finish/rollback of an interrupted adoption stays supported. After a committed adoption, rollback to a Python runtime is refused; the prior owned bytes are not re-activated. |
| Upgrade proof | Repository holds no Python, including inside fixture archives. In-repo adoption tests use captured state snapshots (receipts, journals, lock/owner files, hook configuration) with opaque owned-target bytes. Real v0.0.14 → Rust adoption is proved once per release in qualification, using the published signed v0.0.14 artifact on a disposable host outside the repository. |
| Download transport | Keep `curl` (existing stated dependency); `download-failure-v1` and its `curl_exit` guidance are unchanged. |
| Signature | Keep `ssh-keygen -Y verify` with pinned allowed-signers. No second signature format. |
| JSON numbers in passthrough values | Emulate CPython exactly (below); no contract change. |
| Legacy Python tree | Rust installs at a new owned runtime path; the Python source tree stays in place until explicit uninstall. |
| Explicit-source installs | `--development-source` is retained and refuses without a prebuilt `target/release/am`; the installer never runs a compiler. Managed `--remote/--ref` channels are dropped and refuse with re-bootstrap guidance. Signed releases are the only update channel. |

## Structure and shared contracts

Use one Cargo package with a reusable library and one `am` binary; retain the installed `agent-memory` command via the existing owned-target lifecycle contract. Organize domain modules, not a crate per old Python file. The CLI and harness handlers dispatch to typed domain functions, not shell command strings or arbitrary runtime module loading.

Shared primitives are strict JSON decoding, restricted Markdown frontmatter, bounded ordinary-file reads and observations, canonical hashing, private-path trust checks, monotonic deadline accounting, checked subprocess ownership, Git invocation, durable atomic writes, locking, journals and structured errors. Define these before parallel domain implementations. Domain owners may add their own files but one owner controls shared primitives and the CLI dispatch.

Use the Rust standard library and `libc` for system interfaces and `sha2` for digests. JSON and frontmatter codecs are written in-tree because their bytes are contracts (below). Add a crate only for an established parsing or cryptographic primitive; pin resolved versions in `Cargo.lock`. No `build.rs` may execute an interpreter or fetch executable code. `git`, `curl` and `ssh-keygen` remain explicit external dependencies; no second signature format is introduced.

## Codecs

Baseline has 241 JSON encode sites in 17 keyword variants and 163 decode sites in 7 variants (`json-codec-call-sites.json`). There is no single canonical codec.

- One strict decoder core with explicit per-site policy: duplicate keys (reject / last-wins as today), non-finite tokens (reject / accept as today), byte and nesting bounds. Decode policy changes are contract changes, not defaults.
- An order-preserving value type with the number model below.
- Encoders named by contract, each fixed to its baseline parameters: key order (insertion / sorted), separators (`", "`+`": "` / compact), indent, ASCII escaping, trailing newline. Every call site maps to exactly one named codec; a site that measures bytes (e.g. the 2,048-byte assessment bound) uses the same codec for the measurement.
- Client configuration files (Claude `settings.json`, Codex `hooks.json`): reproduce the existing whole-file re-encoding exactly (insertion order, `indent=2`, non-ASCII preserved). The acceptance criterion becomes "unrelated keys, values and order are preserved; bytes equal the baseline re-encoding".
- Golden vectors are generated once from the baseline at `78eaf70`, outside the repository, and committed as data with their source digests. Rust tests consume the data; nothing in the tree executes Python.
- Restricted frontmatter keeps its own grammar and escapes; no general YAML parser.

### Number model

Schema-less passthrough values (client configuration, any site using plain `json.loads`) follow CPython exactly:

- integers of any size are kept as their validated digit lexeme and re-emitted unchanged; never converted through f64;
- a lexeme with fraction or exponent is an f64 parsed as `float(lexeme)` and printed with `float.__repr__` layout (`1e-05`, `1e+16`, `1.2345678901234568e+17`);
- `1e400` decodes to `Infinity`; `NaN`/`Infinity`/`-Infinity` tokens are accepted exactly where the baseline accepts them and refused exactly where it refuses;
- duplicate keys: last value wins at the first position where the baseline uses plain `json.loads`; refused where the baseline installs `unique_object`.

Typed schemas may additionally refuse floats; passthrough never does. Golden vectors (`tests/vectors/json-codec-v1.json`, 24 styles × 16 encode inputs, 57 decode inputs × 3 policies; `frontmatter-v1.json`, 65 read / 6 write cases) were generated from the baseline under this model. Generator and digests are retained outside the repository.

Declared deltas, recorded as `rust` override rows in the vectors: lone surrogate escapes are refused on decode (CPython accepts them) and nesting deeper than 256 containers is refused (CPython's limit is interpreter-dependent). A client configuration file containing either is left untouched with a named refusal.

## Filesystem and process safety

Validate ownership, mode, type and ancestor/link policy with held descriptors and platform syscalls as appropriate. No exists-then-open trust decision, traversal through unchecked symlinks, stale path re-resolution after a reviewed observation, silent permission repair or last-write-wins mutation. Preserve no-follow, identity rechecks, byte limits, router route limit64 and ordinary per-file refusal bound16,384. Preserve source-preserving oversized-bank recovery and recurrence checks.

Use durable writes and journals with explicit readback; do not claim global atomicity across multiple filesystems. Preserve source bytes, provenance, unknown content, private metadata and recorded backups across crashes. Resume or rollback only receipt-owned changes, and never delete durable bank data during runtime removal or language transition. Private-state compatibility must be proved or produce an explicit recovery/migration requirement; caches may be rebuilt only when their derived/non-authoritative status is established.

Child-process ownership must be explicit. Normal successful calls must reap naturally without self-SIGKILL or process-group cleanup as a success mechanism. Any deliberate cancellation policy must be narrow, owned, separately reviewed and observable; process IDs or groups must not be guessed. Avoid detached threads retaining borrowed descriptors or secrets. Preserve bounded deadlines and failure evidence; no automatic retry loop or timeout widening to make the migration pass.

### Coexistence, clocks, processes

- Python helpers started before adoption may still run. Rust uses `flock(2)` (not `fcntl` record locks) on the same paths and writes the same PID/owner metadata, so either runtime observes the other's ownership.
- Clock per OS, fixed: Linux `clock_gettime(CLOCK_MONOTONIC)`; macOS `mach_absolute_time` scaled by timebase (the relation CPython used). No `Instant` for cross-process stamps. The CPython-version gate is replaced by a Rust self-check of the same clock identity; the Linux image allowlist and Darwin "provisional-unqualified" status are unchanged. Wake support is not newly qualified by the port.
- One process rule in the shared primitive: at the deadline, SIGKILL only the owned direct child, reap it, refuse with retained evidence; `RLIMIT_FSIZE` where the baseline sets it; never a process group, never a guessed PID, no retry.

## Harness integration

Retain Codex, Claude, OpenCode and generic-skill contracts. OMP is a first-class peer and must preserve original native source observation, answer-first activation, human/assistant/tool source distinctions, exclusion of provider-private metadata, exact per-source assessment, transactional completion, wake/lifecycle handling, queue/drain ordering and fork/switch isolation. Notification logs are diagnostic evidence, never admission authority. Rust monotonic timestamps must not be assumed comparable with JavaScript hrtime solely because both are monotonic; establish the exact supported platform clock relation or explicitly refuse that capability without weakening ordinary workflow safety. This migration must not treat the old Python image seam or source-bound runtime evidence as qualification of a new Rust process.

## Python-era adoption

The Rust installer MUST recognise each state type below, on the real paths, and either take it over or refuse without mutation. Every row needs a regression against captured v0.0.14 state and one qualification run against a genuine v0.0.14 installation.

| Python-era state | Rust behaviour |
|---|---|
| Install receipt v1 / v2 (`state/agent-memory/install/receipt.json`) | Decode with the receipt codec; verify every owned target against its recorded identity before replacing it; write the new receipt schema only inside the adoption journal. Unknown schema or drifted target: refuse, name the target. |
| Journal v1, committed history (`journal-*.json`) | Preserved byte-for-byte; never rewritten or pruned by adoption. |
| Journal v1, in flight (`journal.json` mid-transaction) | Finish or roll back using the recorded steps if every step kind is known; otherwise refuse and direct to the retained evidence. Never start adoption over an open journal. |
| Lifecycle `owner.json` / `lock` | Same path, same `flock` class, same PID-metadata format. A live Python owner blocks adoption (busy refusal); a dead owner follows the existing recovery rule. |
| Wrapper bytes (`bin/am`, `bin/agent-memory`) | Replace only when bytes equal the exact recorded wrapper for the receipt; otherwise refuse as foreign. |
| Client hook commands (`/bin/sh …/python3.sh …/*.py` in Claude `settings.json`, Codex `hooks.json`, OpenCode plugins) | Recognise the exact prior command strings; rewrite only those entries to the Rust binary; unrelated configuration follows the config codec rule below. |
| Activation blocks (sentinel-delimited, hashed) | Verify recorded hash; replace block content only; a modified block is a refusal. |
| OMP binding and extension target | Re-issue binding for the Rust artifact digest; `rollout_attested` must be supplied again explicitly; never inherited. |
| Managed source channel clone | Left in place as inert history until explicit uninstall; no longer executed. |
| Private state (`writes/<bank>/…`: `omp-stream-v1`, `turn-sources-v2`, `omp-source-v1`, barriers, pins, ledgers), developer and project registries, bank `.agent-memory.lock`, transaction/recovery markers, purge journals | Read in place with format-exact codecs. No migration, no re-encoding on read. Any format Rust cannot prove it reads exactly produces an explicit pending/recovery requirement, never a rebuild of authoritative state. |

The old updater's behaviour against a published Rust release (refusal before activation, exact message) MUST be observed with the real v0.0.14 runtime before publication; release notes carry the re-bootstrap instruction.

### Running Python helpers

Rust installs at a new owned runtime path; adoption does not move, rewrite or delete the Python source tree at `XDG_DATA_HOME/agent-memory/source`. It stays importable for already-running helpers and is removed only by a later explicit uninstall of the legacy tree. Adoption commit additionally requires the existing quiescence gates (`--omp-peers-upgraded`, layout quiescence) and prints the restart notice; a running `omp.ts` keeps its old spawn target until the harness restarts.

## Bootstrap, release-v2 and delivery

- `install.sh` (POSIX sh, no embedded program): select target from `uname -s`/`uname -m`; create a private 0700 temporary directory; `curl` the per-target `am` binary and its `.sshsig`; verify with `ssh-keygen -Y verify` against allowed-signers pinned in the script; only then execute it. No JSON parsing, hashing tool, Perl or Python in the shell.
- The verified binary re-checks the complete release with trust roots compiled into it: signed manifest, archive digest/size, per-target binary digest/size, then performs install/adoption.
- Manifest schema `agent-memory/release-v2`: version, tag, repository, portable-pack archive (size, sha256, `artifact_digest`), `targets` map (triple → binary size, sha256, per-target `artifact_digest`), and a signed `command_surface` declaration. Same-version identity compares the per-target `artifact_digest`.
- `command_surface` is generated from the binary's parser table and tested for equality with it; update compatibility compares declared surfaces and never executes the candidate to discover them.
- Limits: portable pack keeps 2 MiB per asset / 16 MiB total. The binary is a separate signed asset with its own declared cap (64 MiB) and lives once in the owned runtime location; it is not copied into each client target. `agent-memory` is an owned alias of `am`.

### Binding the bootstrap binary to its release

- Binary signatures use namespace `agent-memory.release-binary`; manifests keep `agent-memory.release`.
- The shell passes the verified binary's own path to it. The binary refuses unless the signed manifest's version equals its compiled version and the sha256 of the bytes at that path equals `targets[<compiled triple>].sha256`. It installs those same bytes; it never downloads the binary again. Version-pinned URLs (tag, not `latest`) are used for every asset after the first.

### Bootstrap-stage failures

Failures before the binary runs (unsupported target, missing `curl` or `ssh-keygen`, download failure, signature failure) print one fixed JSON line with schema `agent-memory/bootstrap-failure-v1`: constant strings per stage plus integer curl exit / HTTP status only; no interpolated text. No private diagnostic file at this stage. `--help` exits 0. `download-failure-v1` remains the contract for every download the binary performs. The new schema is an addition, not a change to the existing one.

### Artifact digest

One definition everywhere (receipt targets and `artifact_files`, OMP binding `artifact`, same-version identity, doctor, migration plans): the existing inventory digest computed over the portable pack files **plus** the installed binary as an inventory entry (`bin/am`, sha256, mode). A swapped binary therefore changes the digest.

- The signed manifest's top-level `artifact_digest` stays pack-only; `targets[<triple>].artifact_digest` is the runtime digest for that target. A receipt is compared with the per-target value.
- Rust-era receipts use a new schema, `agent-memory/install-receipt-v3`: `artifact_files` includes the `bin/am` entry and `source.target` names the compiled triple. `install-receipt-v1`/`-v2` are read only as adoption inputs. A leftover Python runtime that reads the same receipt path refuses the unknown schema instead of misreading it.
- Migration codecs are compiled into the binary (`migration-catalog-v2`), so a migration plan binds the runtime digest, not the pack-only digest: a plan must not resume under a different binary. Python-era in-flight plans (pack-only digest, `migration-catalog-v1`) refuse and point to the retained evidence.
- OMP `rollout_attested` is never inherited when adopting a Python-era receipt (v1/v2) and must be supplied again; a v3 receipt whose reader capability is current is reused on update and doctor without the flag, as before.

### Explicit-source installs

- `--development-source PATH`: requires a prebuilt `am` for the host inside that source (path stated in the refusal) or a developer-run Cargo build; the installer never invokes Cargo.
- Managed `--remote URL --ref BRANCH` channels and `staged()` channel updates: existing managed-channel receipts are adopted read-only; `am update` on them refuses with re-bootstrap guidance. Signed releases are the only update channel.
- Out-of-band recovery (README 260–264): becomes "run the verified bootstrap binary with `recover`".
These are contract changes forced by removing the interpreter; they are listed for operator visibility in the release notes.

### Python removal

Produce native release artifacts for the actually supported macOS/Linux architectures. Artifact verification must precede activation and use trusted verification roots outside the unverified candidate. Bootstrap/install/update/uninstall/doctor/pack validation/release signing/evaluation/test gates must all be Rust or minimal shell calling Rust/platform tools. Source development may require Rust; consumer installation must not require Cargo or any interpreter. Preserve default/custom client targets, copy/link modes, restart notices, guarded upgrades, idempotence, partial-update recovery and rollback.

The delivered Git tree and release payload must have no Python source/bytecode, Python launchers, interpreter probes, dependency declarations, Python CI jobs, Python executable examples or indirect Python build/test requirements. Do not erase historical facts or Git history to disguise the old implementation. Active guidance must be migrated; historical research/evidence may truthfully name the prior runtime but must not route a consumer into executing it.

## Acceptance criteria

- On a consumer host without Python installed, the signed installer verifies and installs the release; `am` operates without locating an interpreter; install/update/uninstall preserve the existing bank; rewritten client configuration keeps unrelated keys, values and order, with bytes equal to the baseline re-encoding.
- Every existing public command has its complete Rust behavior, with the same meaningful JSON/schema, refusal and exit semantics, or an explicitly approved and fully migrated contract change. No placeholder, mock, unsupported-operation shim or Python fallback ships.
- Existing v1 banks and source-preserving layout recovery work through the public CLI, including over-capacity contexts, router64-route boundaries, malformed/duplicate-key metadata, identity conflicts, symlink/permission races, interruptions and lost responses. Every source byte remains accounted for and recurrence prevention still operates.
- A lesson captured/admitted/published from one isolated clone is recalled by a fresh independent clone without changing unrelated code, staged state, identity or provenance; removal of derived caches does not lose canonical memory.
- OMP actual stock-harness source authority, queue/switch/fork isolation, completion and wake tests pass against the Rust executable; Codex/Claude/OpenCode integration contracts also pass. Controlled fixtures alone do not establish native compatibility.
- Rust contract coverage accounts for every existing registered behavioral obligation and negative control. The narrowest meaningful checks run once per completed slice; shared verification runs after integration. Default tests are isolated, credential-free and network-independent. Model/endpoint campaigns keep their explicit authorization and budget boundaries.
- Signed release artifacts for supported targets verify with the pinned trust policy, contain no Python, and are installed/exercised from the actual artifacts; source builds alone do not establish delivery.
- Final repository/payload checks reject Python source/bytecode/launchers/interpreter/build/test dependencies and stale active executable documentation. Historical references are explicitly non-executable evidence, not concealed legacy entrypoints.

## Exclusions

No bank-format redesign, memory deletion, provider/model change, graph-store migration, v0.0.16 scope expansion or rewriting Git history. No promise that switching to Rust by itself fixes performance or proves #206. New release evidence must bind the actual Rust source and artifact; old Python PASS receipts remain historical only.
