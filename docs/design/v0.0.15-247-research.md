## How / ordered execution / method / outputs

1. **Build the policy boundary and shared assumption ledger.** Trace all four issue ACs and each ADR-0008 failure guarantee to planned sections. Separate current same-repository publication/admission from hypothetical export. Exchange an initial assumption table with #246: stable identity/member authority; metadata versus body visibility; source/destination-specific grant; project removal/revocation; stale/offline behavior. Access to two repositories, public hosting and developer attribution are not export authority.
2. **Create a hypothetical scenario inventory.** Use public→public, public→private, private→private and private→public directions. Include changing repository visibility; an allowed reader who lacks export authority; grant changed while projection is built; a recipient removed from membership; source project removal; source deletion/correction; a stale cached copy; inaccessible evidence; missing relation target; federation/network outage; and lost index/graph. Use synthetic identifiers/content only and do not connect or transfer actual banks. Each scenario records actor, authority, precondition, attempted operation, desired disclosure boundary, invariant, alternatives and unresolved owner.
3. **Compare consent and export eligibility.** Define separate decisions for source approval to export, named destination acceptance and reader visibility. Compare per-record/per-version grants, explicitly scoped renewable grants and manually reviewed snapshot publication; contrast implicit export as disallowed. Eligibility table covers admitted/current qualified facts, branch-conditional admitted facts, procedure candidates versus separately approved procedures, orientation prose, externally sourced evidence, superseded/revoked/expired material and private identifiers. Hard exclusions: unadmitted session/branch observations, quarantine, secret-bearing and deleted content can never become exports merely because locally retrievable. Admission alone, a public repository or read permission is insufficient. Branch admission does not grant universal applicability; unknown provenance/applicability or missing consent remains unexportable/pending. Compare redacted summaries against pointers without claiming either removes the need for authority or evidence review; re-export/derivation requires its own explicit policy.
4. **Specify proposed provenance and scope envelope options.** Compare source-project/stable-record/version identity, immutable source/evidence reference, lifecycle/valid time, trust/source class, originating developer separately from harness/session, applicability predicate, destination/access scope, consent authority/version and projection-source revision. Preserve source identity/conditions and uncertainty through ranking, summarization and derived links; never relabel received data as native current guidance or a binding procedure. Define treatment of evidence that cannot be disclosed or revalidated: withhold/abstain or explicitly historical bounded reference, not invented verification. Document information-minimal auditing that cannot leak excluded content; developer ID is not an ACL.
5. **Analyze revocation/removal/deletion options as state transitions.** Compare online revalidation, expiring/renewable export snapshots and bounded cached grants; model publication, scope narrowing, correction, revocation, deletion, member removal, project removal, outage and reconnection. Distinguish stop future selection, invalidate controlled caches/projections, remove projected content and record minimal safe revocation/deletion markers from deletion of the source bank. Removing a project removes its projected content without deleting its bank. Rebuild/rejoin/stale replay must not resurrect removed/deleted content. Discuss races, in-flight queries, backups, retained recipient copies and evidence references; do not promise revocation erases already disclosed bytes, independent clones or Git history. Compare enforceable guarantees and residual risks, including what requires a future service rather than local tooling. Tombstones must not contain deleted body, secret excerpts or reversible/low-entropy hashes.
6. **Analyze dangling links and failure independence.** Produce explicit guarantees/options table: (a) removed index/graph leaves canonical project Markdown untouched/readable; (b) federation unavailable never blocks local initialize/checkpoint/resume/search/validate/repair; (c) missing/removed project target yields a labeled unavailable relation, not corrupt source/target banks, leaked private target identity, or silent link repair; (d) stale/unauthorized/unverifiable federation result is unavailable, not a successful no-match or current qualified guidance; (e) recovery rebuilds only from currently eligible authorized exports. Compare fail-closed cross-project reads with local-only continuation versus bounded offline reads under a valid grant. Recommend a policy boundary only after visibility/revocation tradeoffs are explicit; no weakening local functionality to make remote guarantees convenient.
7. **Recommend by constraint-first scenario comparison.** Reject options violating source hard exclusions, consent, provenance/scope, non-resurrection or local independence. Compare survivors for leakage risk, revocation freshness/enforceability, operator effort, offline usefulness, reproducibility/auditability, complexity and interoperability. Use evidence-backed qualitative rationale and sensitivity to grant/retention assumptions, not invented performance/security scores. State recommended minimum implementation boundary, rejected alternatives, threat limits and decisions requiring explicit operator/source-owner approval. A recommendation to defer sharing is valid research output. Missing stakeholder input is recorded, not a research-start blocker.
8. **Join #246 assumptions before final review.** Draft independently; neither waits for the other's feature or graph. Reconcile identity, authority, metadata versus content visibility, grant version, revocation/removal and outage semantics. Each final brief cites the shared join ID and the partner's pre-join revision, not its own final hash. A separate canonical join record in review evidence binds that ID, both final brief blob hashes, agreed assumptions, disagreements and decision owners. Review the record and exact final bytes independently; if either brief changes after review, its earlier verdict no longer applies and the changed bytes and updated join require re-review. This is research integration, not an implementation dependency.
9. **Independent review, operator disposition and delivery.** Obtain independent technical review of exact brief/coverage/scenario/join bytes (Opus in the requested milestone review); revise blocking defects and re-review. Operator dispositions the recommendation and remaining decisions one question at a time, separately from acceptance of the brief as a complete reviewed research record. Defer or reject of the recommendation can still result in valid v0.0.15 research delivery when the artifact itself is accepted; no disposition approves #57. Integrate the accepted record and evidence through normal repository process and include it in published v0.0.15; parent owns acceptance/integration/release recording.
