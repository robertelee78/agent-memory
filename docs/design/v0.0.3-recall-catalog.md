# Proposed disposable validated-metadata catalog for quick harness recall

Existing #98 / ADR-0005 growing-bank recall. Proposed by codex-root; technical
review required before implementation. The operator says40seconds is too much;
a warm lookup budget question (recommended2seconds excluding harness reasoning)
is pending. No performance acceptance or new user approval is inferred.

## Evidence and intended outcome

The actual50k semantic workflow found the correct lesson through the same three
nodes, but its three public operations spent12.34/13.29/13.88seconds in discovery/
qualification. The bounded cold-path refinement is independently approved with
recall-output privacy requirements. That refinement removes redundant work, but
full parsing on every lookup cannot provide quick ordinary use.

A separate filesystem-only microbenchmark (not bank/quality qualification) used
50,001regular files of roughly1KiB: current complete hashing took1.42–1.46seconds;
Path-based stat inventory0.41seconds; direct scandir metadata inventory0.10seconds.
This suggests preserving an actual final complete hash check while reusing the
runtime's authenticated format-validation work may fit a small warm budget.

## Authority and storage boundary

Markdown and its actual Git repository remain the sole durable memory. Add an
optional, disposable per-repository/worktree **metadata catalog** outside the
checkout and executing runtime. No learning bodies, embeddings, semantic judgments
or source-assertion truth are stored in it. It is not a second memory bank and is
never shared by Git, copied between repositories or shipped in consumer artifacts.
No database/service/MCP/provider/model dependency is required; a bounded JSON
immutable generation is sufficient. Removing/corrupting/losing it leaves the
existing complete file-based reader available and rebuilds from Markdown.

Catalog fields contain only the code-version-bound result of the native complete
bank format/layout validation, source path/hash map, structural scope/lifecycle/
ID/version entries, possible correction/supersession references, oversized-source
inventory and a physical/stat hint manifest. Use compact encoded rows/path
interning if needed; finite per-generation encoded budget is256MiB, below the
existing512MiB private-operation budget. No full source body, origin/evidence
prose or keyword content index is needed for this first exact semantic-selection
fast path. Literal/global-text operations retain the existing reader fallback.

Only the trusted runtime can seal a catalog after its own successful complete
checked observation/recheck. It must not accept a caller's serialized
`prevalidated:true`, metadata cache or external catalog as authority. Bind it to
actual repository/bank/project/settings identity, exact canonical path/hash map,
physical structure, and the actual loaded validator/schema/runtime version.

Protect generation integrity with a fresh automatically managed32-byte local
HMAC key in strict owner-only runtime state, separate from the release-signing key.
No operator enrollment, external trust or key ceremony is required. The key is
operational cache metadata, not project/personal memory. Atomic creation/readback,
private parents/regular-single-link files and source/checkout exclusion follow the
existing trusted-path/state primitives. Never log the key. Loss/invalid state
cannot lose canonical learning: ignore/rebuild the optional catalog. Authenticated
headers/payload sizes/digests must be checked before consuming derived metadata;
unknown/corrupt/oversized formats fail to the complete canonical path.

Generations are immutable and atomically published through an observed small
pointer. Concurrent readers never read a database being updated in place. Worktrees
have separate view bindings. A publication race may discard/retry optional cache
work, never overwrite newer state or turn a cache error into successful absence.
Reclaim only known owned derived generations; preserve foreign/recovery evidence.
Terminal deletion invalidates/removes affected owned catalog generations; no old
catalog can restore deleted content, and this catalog never retains learning bodies.

## Local trust scope and coherent loaded-engine generation

The HMAC protects against accidental corruption and untrusted repository/input
content, within the already trusted executing runtime and local principal. It
DOES NOT isolate a hostile same-UID process that can read the cache key, replace
the user's installed runtime or modify its memory. No such OS isolation is
claimed. No CLI accepts a caller-selected catalog/key path or a serialized
prevalidated witness; sealing is an internal consequence of actual native
validation. Mere ownership/checksum flags never authenticate caller JSON.

Use an explicit native-v1 validator dependency closure. Import that audited
closure before taking a generation; include actual loaded Python function/method
code objects, defaults, declared policy constants/regexes and the actual loaded
schema/model data, plus Python implementation/cache-tag/version and cache-codec
identity. Normalize only supported known immutable/JSON policy roots; unsupported
or unstable state disables the fast path. Fingerprint actual objects/schema
values rather than read their current filename and assume it matches loaded code.

Also snapshot the complete executing package code/schema content manifest at
package startup, before validator imports, and require it unchanged at generation
capture, sealing and qualified output. Include its digest in engine identity.
This covers not-yet-used package dependencies; actual loaded bytecode/schema
fingerprints additionally distinguish stale bytecode or mixed imported objects.
Every validator/cache module must resolve inside that executing package's ordinary
source set. The initial native-v1 closure must be explicit/auditable: unexpected
native dependency loading during validation, an unbound dependency, source-file
change, namespace substitution or inability to establish that closure means no
cache publication/reuse and the full reader remains available. No bare version or
timestamp is sufficient. Known standard-library semantics are bound to the trusted
Python runtime identity; no isolation from a compromised interpreter is claimed.

Capture the generation before native complete validation and recheck it before
sealing its witness. Warm qualification checks the same authenticated generation
before using structural metadata and again before output. The CLI has no
untrusted Python callback during those stages; schema/policy roots are runtime
constants. Any uncertain/mixed generation is a cache miss, never a guessed match.

Cold-parity ordering is mandatory: discover potential replacement references
before visibility/security/kind/query/result budgets; qualify each replacement's
actual metadata/context/time/trust before invalidating an old version; hidden or
unsafe replacement text still invalidates, and a replacement later superseded
must follow the existing raw algorithm's ordering. Oversized active typed sources
under applicable routes still fail before their record-level applicability gate,
even if unselected. Unknown metadata cannot vanish through an index. All such
reverse tables/oversize/layout witnesses must be covered by the authentication
and exact final content check, and parity must be tested against the full reader.

## Warm path without weaker source-currentness assumptions

Filesystem identity/size/mtime/ctime/type/link observations are **hints only** to
find a potentially matching authenticated catalog. They never establish that
canonical bytes are unchanged. A source edit preserving timestamps, a forged hint,
clock anomaly or mmap write still cannot license a returned stale result.

For a completed semantic trace/exact discovered paths, authenticate the catalog
and retain its full native format-validation witness. Resolve only actual selected
record IDs/paths, their potential qualified invalidators, relevant ancestor scopes
and the global oversized-active-source guards. Read/parse those actual bounded
canonical files and apply the same fresh context/time/trust/type/visibility/safety/
correction/deletion rules as the complete reader. A hidden/unsafe replacement can
still invalidate the old source. Trace sources remain mandatory in comparison;
empty semantic selection never becomes an inventory query. Do not cache policy
outcomes or factual/semantic truth.

**Before any usable output, stream/hash the entire actual canonical inventory
and check physical aliases/types/deletion namespace, markers/location/scope/Git.
It must exactly match the authenticated validated catalog and original trace.**
A final cheap physical/stat recheck can detect late additions/changes. This final
actual whole-content hash is mandatory even when all stat hints match. Therefore
no OS-metadata-only freshness assumption replaces the current integrity boundary.
If actual bytes differ, discard the fast observation and reconcile/rebuild through
the complete path; an old trace cannot be silently rebound to new sources.

A private attestation reuses *this runtime's validation of these exact bytes*;
current actual content equality is independently re-established before output.
No untrusted cache field or source assertion is accepted merely because it has a
checksum. The HMAC, exact source hashes, actual loaded engine/schema identity and
actual complete final content check are all necessary. Code/schema changes force
rebuild. A package update during a running process cannot bless a cache from a
different loaded validator; bind loaded code/schema identities, not merely a
version string or current on-disk filename.

Limit the initial fast path to supported semantic/exact-source recall. Keep legacy
keyword/global inventory behavior and comparison/write operations on their current
complete path until separately qualified. Every successful full reader may warm
this catalog from its internally validated operation-local observation; existing
refresh readback can therefore prepare the next turn without another parse just
to create an index. A changed bank may require a heavier rebuild; do not call that
a warm hit. Missing/unavailable cache is a performance miss, not a memory failure.

## Discovery and result contracts

Warm discovery may use an authenticated catalog reference with fresh stat hints to
supply untrusted root navigation, explicitly pending actual complete content
qualification. It must not claim current full inventory/validity from hints.
The final qualified source operation always performs the actual complete hash
check above. Cold discovery retains the approved limited streaming-fingerprint
path. Bounded node operations remain navigation-only.

Preserve the approved read-output privacy amendment: no newly observed per-source
hashes/labels for excluded sources may escape via cache diagnostics, returned
trace/request or errors. Qualified results keep actual source labels and evaluation
time. Global counts not actually reevaluated on the selected fast path must not be
misreported as a complete per-record policy scan; label metric/filter coverage.
Writes and consequential later use retain native fresh comparison/locked apply.

## Qualification before any claim

Exercise cache miss/hit/loss/corruption/unknown formats, authenticated generation
and code-version mismatch, concurrent publication/immutable reader use, source
change with restored timestamps, new/removed sources and aliases, unknown/changed
markers, final-check races and actual complete-content mismatch. Demonstrate that
metadata hints alone never pass. Direct SHA comparisons—not cache flags—must prove
source equality before returned guidance. A deliberately incomplete/modified
caller catalog must not be accepted. Test hidden/unsafe replacements, expiration,
unknown conditions, stable-ID historical versions, global oversized sources,
empty traced recall and ordinary source/bank/index/HEAD preservation. Test actual
forget and no revival from an old generation.

Measure cold rebuild separately from repeated warm own-operation latency at1k/
10k/50k, with the same meaningful blind questions and current source observations.
Keep all failed attempts/context/model/full-I/O costs. Agree the warm target before
claiming a quantitative pass. This is a proposed technical supplement to existing
#98, not an acceptance verdict, different project or a new canonical memory format.
