### Shared integration contract

#244's layout-frontier-v1 and #249's omp-harness-v1 are independent private-state capability producers consumed by ONE existing-lifecycle preflight extension, not competing rollback implementations. The integration owner (parent omp-work until explicit handoff) preserves the union of requirements/evidence pins across install/update/recover/exact rollback/downgrade/uninstall. Unknown/missing/offline private state must not become compatible. Each feature must work alone; neither waits on the other's delivery. Rollout/quiescence applies to processes that can touch the SAME protected bank/private state; independent clones with separate state are not falsely treated as sharing an index. Older/manual binaries cannot be made safe by markers they never read.

#206's recall catalog/memo changes and #209's pure frontier-components memo share validation_memo but different products/identities. Integrate their exact context lifetime/suspension/restoration and fresh-source checks together; no cache-hit or memo may skip #244 frontier checks, #249 source enrollment/assessment, source safety or publication policy. Changed contracts require caller/reference migration, no legacy proof omission treated as empty.

### Binding cross-story implementation contracts

Per-story technical and operator approvals are start gates. A milestone-wide approval does not hold independently approved stories behind #209's target research; until #209 has its own reviewed delivery contract, it remains Designing and no optimization attempt starts. The milestone integration/release contract still requires every retained story's acceptance.

The integration owner is `omp-work`. Independent technical acceptance owner is a separate, read-only Claude Opus session, never an implementing session; operator approval remains separate. Record the exact acceptance session and immutable candidate before each acceptance run. The #209 acceptance owner owns workload semantics in `daily_use.py` and reviews every controller migration; implementation authors cannot self-certify workload equivalence.

One `runtime-compatibility-v1.private_state_capabilities` array declares supported tokens `layout-frontier-v1` and `omp-harness-v1`; absent means the empty set. One `required_private_state_capabilities()` preflight computes the union per bank from layout holds/bindings, source compatibility markers, saved install bindings, local bank registry and private pending indexes. The bank inventory is the union of all those sources, never an intersection; inaccessible, malformed or offline entries remain unknown/pending and refuse incompatible activation. #244 owns interpreting its persistent hold; #249 owns clearing its source marker only after its complete drain proof. Clearing one requirement cannot clear the other.

Total lock order for code that needs multiple lock families: runtime lifecycle -> bank-wide source barrier -> transport registration -> source completion locks in stable namespace order -> bank write lock. No reverse acquisition, child/helper invocation while holding a lock the child may need, or waiting for a writer while holding its dependency. Ordinary operations needing only a suffix may take that suffix but cannot later acquire an earlier family. A lifecycle command first disables executable bindings and obtains quiescence, then takes the ordered locks, verifies inventories again and activates only after durable readback. If existing call paths cannot respect this order, refactor call boundaries before either feature's lifecycle implementation is approved; never bypass a required check to avoid a deadlock.

Mixed-feature acceptance must cover both capabilities active on the same bank, either one resolving while the other remains pending, old-runtime rollback refused while either remains required, and enabling an omp binding during a pending layout frontier. The last case requires a refreshed layout quiescence attestation including the newly enabled invocation route, not only omp's peer-reader attestation.

#244 owns comparison-v2 semantics and the exhaustive caller cutover, including `daily_use.py`, #206's refresh controllers and any later #209 batch commands. No missing-frontier v1 fallback. The #209 acceptance owner verifies migrated controller workloads/oracles against the baseline. If schema-only migration preserves exact semantic workload, retain the historical diagnostic with the migration proof; a changed workload requires a new baseline and operator reconsideration of any timing target. Each plan must explicitly declare whether semantic-sharing-judgment-v2 changes.
